**하지 않음:** 전역 `alias_damping` 값 변경(v1.24: §3.8의 터미널 자원 한정 전 가중치는 상수 변경이 아니라 규칙이며 전역 감쇠 1.0은 fixture s-011을 깨뜨려 기각), 튜닝 제안기의 어휘 규칙(`when_all`) 자동 제안(v1.24: 규칙은 §6 사전 생성 경로로만 들어온다), 지시어 신호, `verb_methods` 기존 메서드의 삭제·재배열, Round 2 봉인 세트의 게이트 사용.

## 3. 스코어러 변경 (`search.py`; §3.1–3.4는 `search_ranking.json` 상수, §3.6–3.8은 v1.24 결정적 규칙)

### 3.1 `method_order_bonus`
질의 unigram 중 **첫 번째로 등장하는** 동사 인벤토리 토큰 `v`에 대해 `preferred := verb_method_order[v][0]`(v1.13; 파일 순서); `preferred ∈ intent_methods`(§3.3의 교집합)이고 `entry.method == preferred`이면 `+method_order_bonus`, 그 외(동사 없음, 교집합 공집합, preferred가 교집합 밖)에는 0 — 최종 메서드 의도 밖의 메서드를 보상하지 않는다(다중 동사 fixture 단위 테스트 필수). 기존 `method_intent` 신호는 그대로 유지된다. 격자 `[0, 0.5, 1.0]`, **기준값 0**. signals에 `method_order: {"value", "verb", "preferred"}`. **Round 2 prefix 불변(AC-R3-12):** verb 행 집합은 Round 2 T 산출물(`structure_sha256 8106c891…`)과 동일하고, 각 verb의 Round 2 메서드 리스트는 Round 3 리스트의 **exact prefix**다. 기존 메서드의 삭제·재배열 금지; method-safety가 새 메서드를 요구하면 **suffix에만**, 둘 이상이면 메서드 이름 사전순으로 추가한다. 따라서 `verb_method_order[v][0]`은 Round 2와 항상 같다.

### 3.2 `path_coverage_bonus`
`matched := sorted({pt.origin for pt in entry.path_tokens if pt.forms ∩ exp.all ≠ ∅})`(리터럴 경로 토큰의 origin 기준 고유 집합; `forms`는 기존 singular/plural 형태 집합, 노이즈는 `path_tokens` 생성 시 이미 제외), `m := len(matched)`에 대해 `+path_coverage_bonus × m`. 격자 `[0, 0.5, 1.0]`, **기준값 0**. signals에 `path_coverage: {"value", "matched"}`.

### 3.3 메서드 의도 일관성과 abstention 계약 (점수 무관)
`intent_methods` := 질의 unigram 중 동사 인벤토리 토큰들의 허용 메서드 **교집합**(동사 없음 → ∅). `method_intent_consistent := bool(intent_methods)`. **`actionable := method_intent_consistent`.** 응답 payload에 `method_intent_consistent: bool`, `intent_methods: [sorted]`, `actionable: bool`, **`recommended_operation`**(`actionable == true AND len(results) > 0`이면 `results[0].key`, 그 외 `null`)을 추가한다. 의미 구분: `actionable=true, recommended_operation=null` = 의도는 명확하나 후보 없음; `actionable=false, recommended_operation=null` = 제품 abstention. 테스트 4사분면(actionable±, results 유무). `actionable == false`일 때 결과 배열은 **후보 목록**이며 소비자는 `results[0]`을 추천으로 해석해서는 안 된다(MCP 도구 설명·README·응답 스키마 테스트로 고정; 결과 배열 자체는 변경 없음). 정렬·점수에는 영향이 없다. Phase 2 응답 테스트에 네 필드를 추가한다(provenance 블록 불변).

### 3.4 격자·기준값·선택기
`CONSTANT_KEYS`에 두 상수 추가(총 8), 기준값은 둘 다 0 → 새 두 신호의 기여는 기준값에서 정확히 0이며, 고정된 Round 2 B aliases/ranking/inventory를 입력으로 쓰면 스코어러 출력은 AC-R3-02와 같이 Round 2와 동일하다(Round 3의 실제 B 정책에는 `lexicon-r3`·후보·suffix 변경이 들어갈 수 있으므로 "Round 3 B == Round 2 B"를 뜻하지 않는다). `method_mismatch_penalty` 격자를 `[0,1,2,3,4,5]`로 확장. 격자 3·6·4·3·3·4·3·3 = **23,328** 지점(v1.13 정정; 이전 31,104는 산술 오류). **최종 격자(계획 단계 확정, §11):** `method_order_bonus` `[0, 0.5, 1.0]`, `path_coverage_bonus` `[0, 0.5, 1.0]`. **격자 평가기(v1.13):** 상수 격자 단계는 질의별 lexical 점수를 alias 상태당 1회 계산해 두고 격자점마다 production의 `_structural_signals`만 재계산하는 memoized 평가기로 돌린다(`search_operations`와 동일한 정렬 키·deprecated 계수·clamp; 무작위 격자점에서 `search_operations`와 ranked key 전체 일치를 테스트로 보장). 제안기 시험과 D 평가는 `search_operations` 경로를 그대로 쓴다. **선택기 점수:** 상수 선택의 regression 점수는 `regression_effective`를 쓴다; `regression_raw`는 선택·tie-break에 쓰지 않는 진단값이고 fixture negative는 계속 raw 하드 제약이다. **선택기 tie-break(보수성):** seed·regression_effective·fixture 결과가 동일한 지점들 사이에서는 `(path_coverage_bonus, method_order_bonus)`가 작은 쪽을 우선하고, 그다음 Round 2의 기존 tie-break(기준값과의 L1 거리, 사전순)를 적용한다. **fixture 하드 제약(raw):** fixture positive 23건은 top-1 기준 23/23, fixture negative 6건은 **legacy raw 판정** `top1 ∉ forbidden_top1` 기준 6/6. `actionable`/effective 값은 진단으로만 기록하며 raw 판정을 대체하지 않는다(fixture는 제품 의미가 아니라 스코어러 회귀 가드). **fixture 캐시:** 상수 격자 단계에서만 `(상수 튜플, B alias sha)` 키로 캐시; 제안기의 각 시험 조합은 새 alias 상태에서 fixture를 재평가한다.

### 3.6 의도 메서드 티어 정렬 (v1.24, `ordering_rules.intent_tier`)
`intent_methods`(§3.3)가 비어 있지 않으면, 정렬 키의 **최상위 성분**으로 `tier := 0 if entry.method ∈ intent_methods else 1`을 두어 의도 밖 메서드의 op는 점수와 무관하게 의도 안 op 전부의 아래에 놓인다(핀 고정 exact match는 종전대로 맨 앞). `intent_methods == ∅`(동사 없음·교집합 공집합)이면 모든 op가 tier 0이며 순서는 변하지 않는다. 점수(`score`)·`method_intent` 신호는 바꾸지 않는다 — 가산 패널티(`method_mismatch_penalty`)는 그대로 두되 티어가 순서를 결정한다. 근거: s-026·s-029는 의도 밖 메서드 op가 텍스트 일치만으로 정답을 앞섰고 이는 패널티 격자 어느 값으로도 안정적으로 막히지 않는다. 알려진 부작용: s-004('transition issue status')는 GET 정답이 티어로 내려간 뒤 bulk POST op가 'status' 텍스트 일치로 단건 POST 정답을 앞선다(상수 영역, 튜닝에 위임).

### 3.7 선호 메서드 tie-break (v1.24, `ordering_rules.preferred_method_tiebreak`)
정렬 키의 점수 다음 성분으로 `tb := 0 if entry.method == preferred else 1`(`preferred` := §3.1의 `verb_method_order[첫 동사][0]`; 동사가 없거나 `preferred ∉ intent_methods`면 모든 op가 0). 동점에서만 작용하며 점수는 바꾸지 않는다. `method_order_bonus`(§3.1)는 그대로 격자 상수로 남는다(기준값 0; 튜닝이 양수를 고르면 점수 자체가 벌어진다). 근거: s-032·s-036의 POST/PUT 동점.

### 3.8 터미널 자원 alias 전 가중치 (v1.24, `ordering_rules.terminal_alias_full_weight`)
`_score`에서 alias 토큰(`exp.direct`)·규칙 토큰(`exp.cond`)의 필드 적중은 `alias_damping`/`rule_damping`으로 감쇠된다. 이 규칙이 켜지면 **그 토큰이 entry의 `terminal_tokens`(마지막 리터럴 경로 세그먼트의 origin, §6.5b)의 singular/plural 형태와 일치하는 경우에 한해** 해당 토큰의 모든 필드 적중을 감쇠 없이(가중치 1.0) 계산한다; 터미널과 무관한 alias 적중은 종전대로 감쇠한다. 근거: 사용자가 alias로만 지칭할 수 있는 자원(release→version, starred→favourite)이 literal 수식어('project', 'my')의 6필드 일치에 밀리는 구조. 전역 감쇠 1.0은 fixture s-011을 깨뜨리므로 터미널 한정이 핵심이다. `ALL_MATCH_BONUS` 판정은 종전대로 base 적중만 본다.

**적용 범위(v1.24.1, H9 리뷰 F1):** §3.6 티어와 §3.7 tie-break는 **자연어 질의**에만 적용한다. 공백 없는 단일 단어가 2개 이상의 unigram으로 쪼개지는 식별자형 질의(`IssueCreateMetadata`, `createIssue`; `is_identifier_query`)는 exact-name 조회이고 안의 동사는 행위 의도가 아니므로 두 규칙을 끄고(legacy 정렬) §3.8 가중치만 유지한다. 여러 단어 질의는 하이픈이 있어도(`update issue-summary`) 식별자형이 아니다(리뷰어가 보인 `joined_query_forms` 기반 술어의 과잉 예외를 배제).

**정렬 키(v1.24):** 핀 고정 → `(tier, -final, tb, deprecated, key)`; legacy 모드(세 플래그 false)에서는 `(-final, deprecated, key)`로 Round 2와 바이트 동일하다. **데이터 형식:** `search_ranking.json`에 `"ordering_rules": {"intent_tier": true, "preferred_method_tiebreak": true, "terminal_alias_full_weight": true}`(구조 필드; H에 커밋, `PRE_FREEZE_NONVERB_STRUCTURE_SHA256[3]` 갱신, T에서 `structure_sha256`로 동결, 튜닝 불변). `RankingPolicy.ordering_rules`(frozen mapping, 세 키 정확히 요구). 세 규칙은 모두 결정적이며 상수가 아니다(격자·`baseline_sha256` 입력 불변).

## 4. 평가와 게이트

- **대칭 판정식(evaluator):** `held_out pass := top1 ∈ expected_top1_any AND actionable == true`; `negative pass := top1 ∉ forbidden_top1 OR actionable == false`(`regression_negative`·`negative` 공통). **seed와 fixture positive는 raw top-1**(`seed.top1_correct := top1 ∈ expected_top1_any`, §13 스키마; v1.13 — seed에는 동사 없는 r0/r1 레코드 5건이 있어 `actionable` 요구는 설계상 39/39를 불가능하게 한다; held_out은 `actionable` 규칙으로 사전 등록되므로 요구한다). `search_fn`은 `(ranked_keys, actionable)`을 돌려주며, Round 1·2 호출 형태(ranked_keys만)는 어댑터가 `(ranked_keys, actionable=True)`로 해석해 계속 지원된다(과거 판정이 abstention으로 바뀌지 않음; Round 1 테스트 불변). 평가된 negative 벤치마크에는 readiness와 diag가 `negative_raw_top1`(top1 ∉ forbidden만)과 `negative_effective`(판정식) 두 수치를 항상 병기한다; **hidden(held_out·negative) 및 참조 세트의 실패 레코드는 `query` 키를 절대 기록하지 않고 대신 `query_sha256`을 기록한다; query 원문을 포함하지 않는 진단 필드(`id`·`top1`·`expected_top1_any`·`forbidden_top1`·`actionable`·`raw_ok`·`top5` 등)는 허용된다**(v1.19 재진술 — 목적은 허용 필드 제한이 아니라 hidden 평문 유출 방지; v1.18 도입: 15/16 같은 합법적 게이트 결과가 `round3-final.json`에 hidden 평문을 남겨 AC-18b 스캔과 충돌하지 않도록); F/X의 hidden은 `not_evaluated`이며 분기별 계약은 AC-R3-11a/b를 따른다.
- **hidden set(게이트):** T 이후 Round 2 §5.3 계약(Temporary chat + Unpersonalized, 동결 프롬프트, 기계 검사, stateless 검토, 교체 계약, coverage manifest)으로 **새로 생성**한다. **actionability 계약(사전 등록, 기계 검사는 production과 동일한 `allowed_methods()` 헬퍼와 동결 인벤토리 사용):**
  - 규칙 `actionable`(held_out): ① 질의가 동결 동사 인벤토리 토큰을 1개 이상 포함하고, ② 발견된 모든 동사의 허용 메서드 교집합 `intent_methods`가 비어 있지 않으며(evaluator의 `actionable == true`와 동일), ③ `expected_top1_any` 중 최소 하나의 HTTP 메서드가 `intent_methods`에 속해야 한다(라벨과 동결 메서드 의도 표의 정합 — 스코어링 신호인 `verb_methods`와 구조적으로 충돌하는 레코드는 봉인되지 않는다). 프롬프트 문구: "Every held_out query must express a single actionable API intent using at least one action verb whose HTTP method matches the expected operation; if several recognized verbs occur, their allowed-method intersection must be non-empty." 위반은 `record h-00N rejected: actionable`. 테스트 3분기: 교집합 비공집합+expected 메서드 포함 → 통과; 교집합 비공집합+expected 메서드 전부 불일치 → 거부; 교집합 공집합 → 거부.
  - 규칙 `negative-distribution`: negative 8건 중 **정확히 4건은 actionable == true, 정확히 4건은 actionable == false**(같은 헬퍼로 판정). 프롬프트 문구: "Exactly 4 negative queries must be actionable under the frozen verb-method inventory (a recognized action verb is present and the allowed-method intersection is non-empty) and exactly 4 must be non-actionable; prefer no recognized verb for the non-actionable half — do not manufacture conflicting multi-verb phrasings merely to force abstention." **섹션 교체 계약(동결 프롬프트에 포함):** "If a later message starts with `negative distribution rejected` and lists all eight negative ids, reply ONLY with a JSON array of exactly eight replacement negative records, one per listed id, preserving those ids; together they must satisfy exactly 4 actionable / 4 non-actionable. Do not return held_out records or the outer object." 응답은 `validate_replacement_output(obj, 8 ids)` + 분포 검사를 통과해야 한다. **수명주기:** 개별 레코드 교체 뒤에도 4/4 분포를 재검사한다; 깨졌으면 개별 레코드를 임의로 고르지 않고 섹션 교체를 **정확히 1회** 수행하며, 새 8건은 기계 검사·의미 검토를 처음부터 다시 거친다. 섹션 교체를 이미 사용한 뒤 개별 교체로 다시 4/4가 깨지면 두 번째 섹션 교체는 하지 않고 즉시 생성 attempt 전체를 `invalid`로 기록하며, 새 attempt는 **새 stateless/Unpersonalized 호출**(기존 chat 이력 미승계)에서 동일 입력으로 시작한다(attempt 상한은 Round 2와 동일).
  - 규칙 `negative-method`(기계 규칙, actionable negative에만 적용): `methods(forbidden_top1) ∩ intent_methods ≠ ∅`(메서드만으로 밀려나는 쉬운 negative 방지). 위반은 `record n-00N rejected: negative-method`. 의미 검토자는 "정말 잘못된 operation인가"에만 집중한다.

## 6. 어휘 메커니즘

- **타깃 자격(expected_vocab, classify, 사전 게이트 공통):** 제외 집합은 `FUNCTION_WORDS ∪ path_noise ∪ ID_LIKE ∪ STOPWORDS ∪ {숫자}`. 동사 인벤토리·product_hints 소속은 제외 사유가 **아니다**. 단, 타깃 토큰은 해당 seed의 expected op의 **자원 어휘** `resource_vocab(op) := norm_tokens(리터럴 경로 세그먼트 + 종단 세그먼트 + tags)`(후보 타깃도 같은 `norm_tokens` 정규화)에 최소 1회 나타나야 한다(summary·operationId만의 등장은 불충분) — 현재 동결 카탈로그에서 순수 행위 토큰(get/create/delete 등)이 자원 증거를 얻지 않음을 테스트로 보장한다(tag 텍스트에 행위어가 들어올 수 있으므로 규칙 자체의 절대 보장은 아니다). 실제 카탈로그 fixture로 `feedback→comment`(경로 `comment`), `iteration→sprint`(경로 `sprint`), `blog entry→post`(tag "Blog Post"의 `post`)가 허용됨을 테스트로 고정한다. 후보 ⇔ R6 동치 테스트 유지.
- **예산:** alias 총 ≤ 15, **seed당 ≤ 2**, alias당 타깃 1.
- **제안기 원자 액션 계약(결정적):** 원자 액션은 **직접 alias만**(`when_all` 규칙 제안 없음, §2 "하지 않음"; v1.13 명시). seed를 id 사전순으로 순회한다. 각 seed의 원자 액션 = `(candidate_word, target)`; 액션 목록은 튜플 사전순. 시험 순서: 크기 1 액션을 순서대로, 그다음 **서로 다른 candidate_word**를 가진 크기 2 조합을 튜플 사전순으로. 각 시험은 현재 working 스냅샷에서 시작하고 실패한 시험의 변경은 누적하지 않는다(원복). 통과하는 첫 조합만 working에 커밋한다. seed 진입 시 이미 통과면 `resolved_by_prior_change`. 채택된 원자 액션은 seed당 ≤ 2, 전체 ≤ 15. `--verify`는 같은 제안기를 B 상태에서 재실행해 패치·`result_sha256`이 정확히 일치해야 한다(AC-R3-10).
- 사전 재게이트: `feedback→comment`, `iteration→sprint` 류가 통과한다. `release→build`처럼 타깃이 seed의 자원 필드에 없는 항목은 계속 거부된다.
- **구문 동의어 → 조건부 규칙(v1.24):** 정규화 후 **정확히 2토큰**인 사전 키(`"time entry"`, `"blog entry"`)는 alias가 아니라 규칙 `{"when_all": [t1, t2], "add": [target]}`로 병합된다(기존 `rules` 메커니즘, `rule_damping` 적용, §3.8의 터미널 전 가중치 대상). 구조 검사: 두 토큰 모두 `_SHAPE`를 만족하고 동사·기능어·stopword·id-like가 아니며, 두 토큰이 모두 카탈로그 어휘여도 거부 사유가 아니다(`in_catalog`는 단어 키에만 적용 — 구문은 문맥을 더하는 것이 목적); 동일 `when_all` 집합의 규칙이 이미 있으면 `rule_conflict`; 타깃은 단어와 같은 자격(concept 토큰 1개). 사전 게이트: 두 토큰이 모두 등장하는 seed가 있으면 타깃이 그 seed들의 `expected_vocab` 합집합에 있어야 한다(`seed-incompatible`). 캡: 자원당 단어 ≤5, 구문 ≤5(별도 계수). 노트: `rule:<index>` 키에 `{origin: "lexicon-r3", seed_query_id: null, failure_classes: [], evidence}`. 3토큰 이상 키는 `shape`로 거부. 근거: `entry`처럼 다의어인 단어는 단일 타깃 alias로는 한쪽 질의를 반드시 깨뜨린다(프로브: entry→worklog는 s-030을 살리고 s-036을 깨뜨림). 튜닝 제안기는 여전히 규칙을 제안하지 않는다.

## 11. 위험과 완화

- coverage 보너스가 "정답이 얕은 경로" 질의를 깨뜨릴 수 있음 → 기준값 0, 보수적 tie-break, fixture 하드 제약.
- 동사 없는 held_out은 판정식상 실패 → `actionable` 규칙으로 사전 등록(evaluator와 같은 헬퍼). negative는 4/4 분포 고정으로 abstention이 게이트를 비우지 못하며, actionable negative 4건의 raw 통과가 raw 품질의 진짜 게이트다.
- **격자 런타임(v1.13, 계획 단계 실측):** Apple M3 Pro · Python 3.11.15 · 아카이브 Round 2 S(943 ops) · B aliases에서 production 경로 0.2007 s/점(40점 평균) → 23,328점 ≈ 78분; memoized 격자 평가기 0.0454 s/점(20점, ranked key 불일치 0) → **≈ 17.6분**. 결정: 최종 격자는 두 보너스 모두 `[0, 0.5, 1.0]`(축소 없음)이며 `tuning_grid_sha256`은 이 설계 결정의 해시다. 아래 10분 절차는 v1.13에서 **계획 단계 결정으로 대체**되어 적용하지 않는다. (구 문구) 격자 × (seed 39 + neg 14 + fixture 29) → 측정 절차: 같은 S·B aliases에서 전체 격자를 정확히 1회 실행한 wall-clock(도구 오류·timeout은 판정에 쓰지 않음)을 ledger에 기록하고, 10분 초과 시 `method_order_bonus` 격자를 `[0, 0.5]`로 축소. 격자 축소 여부는 **T 이전에만** 결정하고 T 이후 격자 변경은 금지하며, 최종 격자의 canonical sha(`tuning_grid_sha256`)를 freeze에 기록한다(AC-R3-13b). 계획 단계에서 실측해 격자를 미리 확정하는 것을 우선한다(동일 코드가 기계 부하에 따라 다른 격자를 고르는 환경 의존을 피하기 위해, 실측 기계·러너 조건을 ledger에 기록하고, 구현 계획 작성 시 1회 실측으로 최종 격자를 `[0, 0.5, 1.0]` 또는 `[0, 0.5]` 중 하나로 **계획 단계에서 확정**해 `tuning_grid_sha256`이 실행 환경이 아닌 설계 결정의 해시가 되게 한다; 구현 계획은 contingency 문구를 그대로 옮기지 말고 **실제 최종 격자 값**을 수용 항목으로 적는다).
- 새 hidden 생성에는 ChatGPT 사용량이 필요(T 이후, 5시간 창 초기화 후).
- (v1.24) s-028은 §3.8로 해결, s-027('show my starred searches')은 `/filter/my`의 literal 'my' 터미널 매치가 남아 미해결(튜닝 위임); s-004는 §3.6 부작용으로 상수 영역에 남는다. Round 4 후보: 어휘 규칙 자동 제안, 결정어('my')의 자원 자격 재검토.
