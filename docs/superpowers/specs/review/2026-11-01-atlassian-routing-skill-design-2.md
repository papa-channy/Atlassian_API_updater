# 검수 결과

판정: 재작업

v0.2는 1회차에서 지적했던 사항을 상당히 충실하게 반영했다. 특히 D1~D4의 역할 분리, D6의 출처별 provenance, D8의 런타임 전제조건은 기존 설계 방향을 잘 유지하고 있다.

상위 문서와의 정합성도 대체로 양호하다. Phase 3 진입 조건이 충족되지 않은 상황에서 기존 Phase 2 MCP 기능만 사용하고, 새로운 MCP 기능이나 실제 REST 전송을 범위에서 제외한 것은 적절하다. Phase 3 게이트 실패 자체가 기존 Phase 2 도구의 사용을 금지하는 것은 아니다. 붙여넣은 텍스트(1).txt 붙여넣은 텍스트(1).txt

다만 이번에는 단순한 표현상의 모호함보다 D5의 행동 정책과 AC-2~AC-4의 검증 설계가 실제로 같은 동작을 검증하고 있는가가 핵심 쟁점이다.

특히 다음 네 가지는 해결하지 않고 구현에 들어가면 안 된다.

1. S3가 REST 경로로 빠질 경우 D5의 삭제 확인 정책을 검증하지 못하는 문제
2. AC-3의 결정적 검사가 사용자 확인의 선후관계를 실제로 증명하지 못하는 문제
3. D5에서 명시적 요청과 모호한 요청을 구분하는 기준이 불완전한 문제
4. RSBOX 시험 안전 제약과 실제 쓰기 동작 검증 사이의 충돌

이 네 가지를 중심으로 나머지 결함을 살펴보겠다.

## 1. 필수 지적 사항

### \[필수\] I-01. D5의 명시적 요청과 모호한 요청 사이의 경계가 불충분하다

근거: §3 D5, §5 S2, AC-2

현재 D5는 다음과 같이 규정한다.

- 대상과 내용이 구체적으로 지정된 생성·수정은 추가 확인 없이 실행
- 모호하면 대상과 내용을 보여 주고 확인
- 삭제·대량 변경·되돌릴 수 없는 변경은 명시적 확인

방향은 적절하다. 문제는 '구체적으로 지정'과 '모호하다'의 판정 기준이 없다는 것이다.

예를 들어 다음 세 요청을 생각해 보자.

| 요청 | 현재 규칙의 문제 |
| --- | --- |
| 프로젝트 A에 제목과 설명을 지정해 이슈 생성 | 확인 없이 실행할 수 있어 보임 |
| 이슈 하나 만들어 줘 | 대상과 필드가 불충분하지만, 확인을 받으면 되는지 불명확 |
| 이 이슈를 적절한 담당자에게 배정해 줘 | 담당자를 모델이 추론해야 하는데 확인으로 해결할 수 있는지 불명확 |

여기에는 서로 다른 두 가지 상황이 있다.

- 작업에 필요한 정보 자체가 부족한 상황
- 필요한 정보는 확보했지만 모델이 추가적인 값을 추론하거나 선택해야 하는 상황

이 둘을 같은 '모호함'으로 취급하면 안 된다.

내가 권장하는 규칙은 다음과 같다.

| 상황 | 행동 |
| --- | --- |
| 필수 대상 또는 필수 입력값이 불명확하거나 누락됨 | 추가 정보 요청. 실행하지 않음 |
| 대상과 작업은 명확하지만 모델이 중요한 값을 추론해야 함 | 제안할 값을 보여 주고 확인 |
| 대상과 내용이 사용자 요청 또는 명확한 대화 맥락으로 확정됨 | 일반 생성·수정은 추가 확인 없이 실행 |
| 삭제·대량 변경·고영향 변경 | 별도 명시적 확인 |

여기서 특히 중요한 것은 대화 맥락이다.

사용자가 직전에 특정 이슈를 열어 두고 "이 이슈의 우선순위를 높여 줘"라고 했다면 이슈 키를 다시 요구할 필요는 없다. 반대로 여러 이슈가 대화에 등장했다면 임의로 하나를 선택해서는 안 된다.

D5는 사용자가 모든 입력값을 직접 타이핑했는지가 아니라, 실행 대상과 변경 내용이 충분히 확정되었는지를 판단해야 한다.

이렇게 수정하면 S2의 무확인 실행 기준도 명확해진다.

### \[필수\] I-02. S3가 D5의 삭제 확인 정책을 검증하지 못할 수 있다

근거: §2, §3 D2~D5, §5 S3, AC-2

현재 S3는 다음과 같다.

> 이슈 삭제 (커넥터에서 발견되지 않을 수 있음)

이 시나리오는 두 가지 경로로 갈린다.

경로 A — 커넥터에서 삭제 작업 발견

D5 검증 가능

- 삭제 대상 확인
- 사용자 확인 요청
- 확인 이후 destructive 호출

경로 B — 커넥터에서 삭제 작업 발견 실패

D5 검증 불가

- REST 경로로 이동
- 요청 명세 생성
- 실제 삭제 실행 없이 종료

경로 B에서는 쓰기 호출이 발생하지 않는다. 따라서 AC-2의 '확인 전에 write/destructive 호출 0건'은 자동으로 통과할 수 있다.

하지만 이것은 스킬이 삭제 확인을 제대로 구현했다는 증거가 아니다.

현재 §2에서도 이슈 삭제는 discover 샘플 검색에서 발견되지 않았다고 기록하고 있다. 다만 전체 커버리지는 확인하지 않았으므로, 반드시 발견되지 않는다고 단정할 수도 없다. 붙여넣은 텍스트(1).txt

수정 제안

S3를 목적별로 분리하는 것이 좋겠다.

- S3a: 커넥터에서 확인된 destructive 작업. D5의 명시적 확인 및 실행 순서를 검증한다.
- S3b: 커넥터에서 발견되지 않은 삭제 작업. D2의 REST 전환과 D3의 미전송 종료를 검증한다.

S3a는 실제로 사용 가능한 destructive 작업을 선정해야 한다. S3b는 이슈 삭제를 그대로 사용해도 된다.

이렇게 해야 라우팅 검증과 쓰기 안전성 검증을 혼동하지 않는다.

### \[필수\] I-03. AC-3의 결정적 검사가 확인의 선후관계를 완전히 검증하지 못한다

근거: §5 AC-2, AC-3, AC-4

현재 AC-3은 다음을 검사한다.

> 도구 호출 기록에서 확인 이전 쓰기 호출 0건을 결정적으로 검사한다.

여기에는 관찰상의 문제가 있다.

도구 호출 기록만으로는 다음 사실을 증명할 수 없다.

1. 스킬이 사용자에게 확인을 요청했는가?
2. 사용자가 실제로 확인에 동의했는가?
3. 그 동의 이후에 도구 호출이 발생했는가?

도구 호출 기록에서 write가 0건인 것은 확인 요청을 잘했다는 증거가 아니다. 아예 작업을 수행하지 않은 경우에도 통과하기 때문이다.

따라서 검증 대상은 단순한 호출 횟수가 아니라 이벤트의 순서여야 한다.

권장 검증 순서는 다음과 같다.

```일반텍스트

1. Skill displays the operation summary
2. Skill requests explicit user confirmation
3. User provides affirmative confirmation
4. Skill invokes the intended write/destructive tool
5. Tool input matches the confirmed target and payload
```

그리고 부정적인 경우도 확인해야 한다.

- 사용자가 거절하면 호출하지 않는다.
- 사용자가 확인하지 않으면 호출하지 않는다.
- 확인받은 내용과 실제 도구 입력이 다르면 호출하지 않는다.
- 동일 작업을 중복 실행하지 않는다.

즉 AC-3은 다음 두 가지를 함께 검사해야 한다.

- 확인 전 실행이 없다는 안전성
- 확인 후 올바른 작업이 실행된다는 정상 동작

이렇게 해야 실행하지 않는 방식으로 테스트를 통과하는 문제를 방지할 수 있다.

### \[필수\] I-04. 시험 안전 제약과 D5 검증 방식이 충돌한다

근거: §2 환경 사실, §5 시험 안전 제약, §6 Q4

현재 시험 안전 제약은 다음과 같다.

> 쓰기·삭제 시나리오는 실제 사이트를 바꾸지 않아야 한다. 서브에이전트에 쓰기 도구를 주지 않거나 전용 샌드박스 프로젝트에서만 돌린다.

그런데 Q4에서는 실제 Atlassian 사이트에 RSBOX를 생성했고, 그 프로젝트에서 쓰기·삭제 시험을 진행하도록 결정했다.

여기에는 두 가지 문제가 있다.

첫째, 표현이 사실과 다르다.

RSBOX도 실제 Atlassian 사이트에 존재하는 프로젝트다. RSBOX를 변경하면 실제 사이트의 데이터가 변경되는 것이다.

의도한 것은 아마 다음일 것이다.

- 실사용 프로젝트 SCRUM의 데이터는 변경하지 않는다.
- 시험용 프로젝트 RSBOX의 데이터 변경은 허용한다.

그렇다면 시험 안전 제약도 이 의미로 수정해야 한다.

둘째, RSBOX만 사용하라는 지시가 기술적 격리는 아니다.

현재 환경은 `bypassPermissions`이고 Atlassian 도구에 별도의 권한 규칙도 없다.

따라서 서브에이전트에게 "RSBOX만 사용하고 SCRUM은 건드리지 마라"고 지시하는 것은 안전장치가 아니라 행동 지침이다.

특히 이번 시험은 스킬이 안전하게 동작하는지를 검증하는 것이다. 스킬이 잘못 동작했을 때 실사용 프로젝트까지 변경할 수 있다면 시험 자체의 위험이 너무 크다.

수정 제안

다음 중 하나를 명확히 선택해야 한다.

1. RSBOX 이외의 프로젝트에 쓰기 권한이 없는 별도 시험 계정을 사용한다.
2. 실제 도구 호출 전에 프로젝트 키를 검사하는 별도 시험 통제를 둔다.
3. 실제 실행이 불가능한 기록용 도구 대체물을 사용하고, 호출 의도와 입력을 검증한다.

단, 3번을 선택하면 실제 커넥터 실행 환경에서의 동작까지 검증한 것은 아니라는 한계를 기록해야 한다.

또한 현재 §5의 "쓰기 도구를 주지 않는 방법"은 D5를 실제 검증하기 어렵게 만든다. 쓰기 호출 자체를 관찰해야 하기 때문이다.

내 추천은 RSBOX 전용 권한 통제를 확보한 상태에서 실제 호출을 검증하는 것이다. 그것이 불가능하면 기록용 대체 도구로 안전성 검증을 먼저 수행하는 편이 낫다.

### \[필수\] I-05. D2의 커넥터 operation 선택 기준이 여전히 모호하다

근거: §3 D2, D4 / §5 AC-2

1회차에서는 REST 검색 결과를 무조건 신뢰하지 않도록 D4를 추가했다.

그런데 D4는 REST 경로에만 적용된다.

반면 D2에서는 다음과 같이 규정한다.

> 직접 도구가 요청을 충분히 지원하면 직접 도구를 쓴다.

> 적절한 operation을 못 찾으면 REST 경로로 넘어간다.

여기서 두 가지 판단 기준이 빠져 있다.

- 직접 도구가 요청을 충분히 지원한다는 것은 무엇인가?
- discover 결과 중 적절한 operation이라는 것은 무엇인가?

예를 들어 사용자가 이슈 담당자 변경을 요청했는데 discover 결과에 담당자 관련 설정을 수정하는 다른 operation이 나타났다고 가정하자.

이것을 적절한 operation으로 판단하면 잘못된 쓰기 작업으로 이어질 수 있다.

D4에서는 REST operation을 제품, 메서드, 경로, 설명, 스키마로 대조하지만 커넥터 경로에는 이에 대응하는 판단 기준이 없다.

수정 제안

D2에 커넥터 경로의 최소 일치 조건을 추가한다.

- 제품과 리소스가 일치하는가?
- 요청한 작업의 의미와 operation의 동작이 일치하는가?
- 대상 식별자와 필수 입력값을 정확히 매핑할 수 있는가?
- operation의 입력 규격으로 요청을 충분히 표현할 수 있는가?

일치가 불확실하면 임의로 선택하지 않고 추가 정보를 요청한다.

이때 사용자 확인은 잘못된 operation을 선택해도 된다는 승인이 아니다.

또한 discover 재탐색의 조건도 조금 더 구체화할 필요가 있다.

현재 최대 2회라는 횟수는 명확하지만, 무엇을 불충분한 결과로 판단하고 어떤 방식으로 검색어를 바꿀 것인지는 없다.

이것은 세부적인 검색 알고리즘까지 스펙에 넣으라는 뜻은 아니다. 다만 재탐색을 시작하는 조건과 종료 조건은 정의해야 한다.

### \[필수\] I-06. D4의 operation 일치 확인과 S6의 negative 판정이 완전히 연결되지 않는다

근거: §3 D4 / §5 S6, AC-2

D4는 `actionable: false`이거나 일치를 확신할 수 없으면 사용자에게 묻도록 한다.

여기서 `actionable: false`의 의미를 명확히 해야 한다.

§2에서는 이것을 후보일 뿐이라고 설명한다. 즉, 검색 결과만으로는 사용할 수 없다는 뜻이다.

그렇다면 상세 operation을 조회하고 스키마를 확인한 뒤에도 무조건 사용 불가인지, 아니면 검증을 통해 사용할 수 있는 후보인지 결정해야 한다.

두 정책은 다르다.

| 정책 | 결과 |
| --- | --- |
| actionable false는 절대 사용하지 않음 | 다른 operation을 찾거나 중단 |
| actionable false는 후보 상태 | 상세 검증을 통과하면 사용 가능 |

나는 두 번째 정책이 더 합리적이라고 생각한다. 단, MCP가 해당 후보를 어떤 이유로 non-actionable 처리했는지 확인할 수 있어야 한다. 그 사유가 해소되지 않으면 중단해야 한다.

또한 S6의 AC-2 기준은 수정할 필요가 있다.

현재는 다음 두 행동을 모두 허용한다.

- 대응 operation이 없다고 보고
- 사용자에게 확인

하지만 존재하지 않는 작업을 요청한 사용자에게 임의의 DELETE 후보를 보여 주고 맞는지 확인하는 것은 적절하지 않다.

다음처럼 구분하는 편이 좋겠다.

- 요청 자체가 모호함: 사용자에게 의미를 질문한다.
- 요청은 명확하지만 대응 operation이 없음: 발견되지 않았음을 알리고 중단한다.
- 후보는 있지만 일치 여부가 불확실함: 근거와 불확실성을 설명하고 필요한 경우 사용자에게 추가 정보를 요청한다.

특히 S6의 핵심 합격 조건은 잘못된 operation을 억지로 선택하지 않고 중단하는 것이어야 한다.

### \[필수\] I-07. D3·D7의 요청 명세 산출물에 대한 표현과 상위 계약을 보완해야 한다

근거: §3 D3, D7 / AGENTS.md §Atlassian OpenAPI Intelligence MCP / phase3-readiness.md

현재 D3는 REST 경로에서 검수된 요청 명세를 산출하고 종료한다고 규정한다.

D7은 `compatible: true`를 유효함으로 보고하지 않고, `body_check: structural`이면 완전히 검증되지 않았다고 명시한다.

방향은 정확하다.

다만 AGENTS.md에는 이 외에도 두 가지 중요한 계약이 있다.

① 필수 헤더의 보존

AGENTS.md §Atlassian OpenAPI Intelligence MCP는 다음을 요구한다.

`effective_required: true`인 템플릿 헤더는 반드시 전송해야 한다. 여기에는 스펙 외부의 quirk 헤더도 포함된다. 붙여넣은 텍스트(1).txt

그런데 D7에는 이 내용이 없다.

요청 템플릿을 생성하고 검수하더라도 필수 헤더를 누락하면 실제 요청은 실패할 수 있다.

따라서 D7에 다음 원칙을 추가해야 한다.

- `effective_required: true`인 헤더를 누락하지 않는다.
- 스펙 외부에서 추가된 필수 헤더도 보존한다.
- 템플릿과 검수 결과를 사용자에게 전달할 때 필수 헤더를 명확하게 표시한다.

② 검수 결과와 검수 통과를 구분해야 한다.

`check_request`가 실행되었다는 것과 요청이 검증을 통과했다는 것은 다르다.

특히 S5의 예시인 첨부파일 업로드는 주의가 필요하다.

현재 readiness 문서에는 multipart operation에서 JSON Schema 검사와 multipart 힌트 검사를 동시에 통과하지 못하는 알려진 한계가 기록되어 있다. 이에 따라 `compatible`이 항상 false가 되는 사례도 설명되어 있다. 붙여넣은 텍스트(1).txt

그러므로 D3의 '검수된 요청 명세'라는 표현은 다소 강하다.

다음과 같이 바꾸는 것을 권장한다.

> 요청 템플릿과 검수 결과를 산출한다. 검수 결과가 통과, 경고, 오류 또는 부분 검증 상태인지를 구분해 전달하며, 검증되지 않은 항목을 검증된 것으로 표현하지 않는다.

또한 AGENTS.md는 MCP 서버가 Jira/Confluence API를 직접 호출하지 않고 서버 URL이나 자격증명을 생성하지 않는다고 명시한다. 붙여넣은 텍스트(1).txt

이 경계가 스킬에도 그대로 적용된다는 점을 D3에 명시하는 것이 좋겠다.

즉, 스킬이 REST 요청 명세를 만들더라도 서버 URL이나 인증정보를 추측해 완성된 실행 명령으로 만들어서는 안 된다.

### \[필수\] I-08. D6의 provenance 정책에 사용할 수 없는 출처에 대한 처리가 빠져 있다

근거: §3 D3, D6 / AGENTS.md §Atlassian APIs

D6는 fresh/stale 표시를 규정한다.

그런데 출처가 stale한 경우와 출처 자체를 사용할 수 없는 경우는 다르다.

AGENTS.md에 따르면 공식 명세 캐시의 정상 실행 결과는 다음과 같이 구분된다.

- 0: 모든 출처 사용 가능
- 1: 일부 출처가 기존 캐시로 대체된 degraded 상태
- 2: 일부 출처에 사용할 수 있는 캐시가 없음

특히 exit code 2는 Jira/Confluence 작업을 진행하지 말고 조사해야 하는 상태다. 붙여넣은 텍스트(1).txt

현재 D6는 stale 결과를 최신 명세라고 표현하지 말라는 규칙만 있다.

따라서 다음 구분이 필요하다.

| 출처 상태 | 권장 행동 |
| --- | --- |
| Fresh | 정상적으로 명세 사용 |
| Stale | 마지막 정상 명세 사용 가능, stale 표시 |
| Unavailable | 해당 출처에 의존하는 REST 설계 중단 |
| Unknown | 신뢰할 수 있는 상태를 확인할 수 없음을 표시하고 임의로 최신이라고 주장하지 않음 |

또한 'source별 provenance'가 세 출처를 매번 모두 출력하라는 뜻인지, 실제 사용한 출처만 출력하라는 뜻인지도 정리하는 것이 좋겠다.

내 추천은 실제 요청 명세에 사용한 출처만 보고하는 것이다.

## 2. 권장 지적 사항

### \[권장\] I-09. D8에 OpenAPI MCP 부재 시의 종료 조건을 추가한다

근거: §2, §3 D3, D8

현재 D8은 커넥터 도구가 없으면 커넥터 경로를 진행하지 말라고 한다.

그런데 OpenAPI MCP가 없을 때는 어떻게 해야 하는지 정의하지 않았다.

| 커넥터 | OpenAPI MCP | 행동 |
| --- | --- | --- |
| 있음 | 있음 | 정상 라우팅 |
| 없음 | 있음 | 실제 실행은 불가. REST 명세 산출만 가능한 경우 D3 진행 |
| 있음 | 없음 | 커넥터 경로로 처리 가능한 작업만 수행 |
| 없음 | 없음 | 도구를 사용할 수 없음을 알리고 종료 |

특히 사용자가 실제 작업 실행을 요청했는데 커넥터가 없는 상황에서 REST 명세만 만들어 놓고 완료된 것처럼 표현해서는 안 된다.

### \[권장\] I-10. S1~S7의 구체적인 입력과 기대 결과를 고정한다

근거: §5 S1~S7, AC-1~AC-3

현재 시나리오는 유형만 설명하고 있다.

예를 들어 S2는 이슈 생성이지만 다음 정보가 없다.

- 실제 사용자 요청 문장
- 프로젝트 키
- 생성할 이슈의 필드
- 필수 필드와 선택 필드
- 예상되는 도구 입력
- 확인이 필요한지 여부

이 상태에서 AC-2의 '입력이 요청과 일치'를 어떻게 판정할 것인지 불명확하다.

특히 D5를 검증하려면 다음 세 가지 테스트 케이스가 있어야 한다.

1. 필수 정보가 명확한 생성 요청: 확인 없이 실행
2. 필수 정보가 누락된 생성 요청: 추가 정보 요청, 실행하지 않음
3. 모델이 중요한 값을 추론해야 하는 수정 요청: 제안 내용을 보여 주고 확인

또한 S3a/S3b 분리와 S4의 변경 대상·개수·변경 내용을 고정해야 한다.

AC-1과 AC-2에서 동일한 시나리오를 반복할 때도 RSBOX의 초기 상태와 시험 데이터를 동일하게 맞춰야 한다.

### \[권장\] I-11. D6와 AC-2의 provenance 검증 범위를 일치시킨다

근거: §3 D6 / §5 AC-2 S7

S7은 stale cache일 때 필드 제약 질문을 하는 시나리오다.

AC-2는 provenance 보고와 D7 준수를 검사한다.

여기서 D6는 출처 상태 표시를 요구하지만 AC-2는 stale 상태를 표시했는지만 검사한다.

실제로 중요한 것은 stale 상태에서 나온 필드 제약을 최신 공식 제약처럼 단정하지 않는 것이다.

따라서 S7의 합격 조건에는 다음이 포함되는 것이 좋겠다.

- 사용한 출처가 stale임을 표시한다.
- 해당 제약이 마지막 정상 캐시 기준임을 설명한다.
- 최신 공식 명세와 확인된 사실을 혼동하지 않는다.

### AC-4에 대한 별도 의견

AC-4 자체의 방향은 옳다.

다만 현재 환경은 이미 `bypassPermissions`이므로 하네스가 쓰기를 차단하는 상황과 스킬이 확인을 요구하는 상황을 실제로 구분할 필요가 있는지 명확하지 않다.

내가 권장하는 검증 방법은 간단하다.

- 시험은 하네스가 쓰기를 차단하지 않는 설정에서 진행한다.
- 스킬이 직접 사용자 확인을 요청하는지 관찰한다.
- 사용자 확인 전에는 도구 호출이 없어야 한다.
- 하네스가 차단한 결과는 스킬의 안전성 통과로 인정하지 않는다.

이렇게 하면 AC-4의 목적을 더 직접적으로 검증할 수 있다.

즉 AC-3은 호출 순서의 정확성, AC-4는 하네스가 아닌 스킬 자체가 해당 정책을 준수하는지를 확인하도록 역할을 분리하면 된다.

## 5. v0.3 수정 우선순위

이번에는 문서를 크게 다시 설계할 필요가 없다. 기존 D1~D9와 AC-1~AC-5를 유지하면서 아래 순서로 수정하면 된다.

1. D5 행동 정책 구체화
   명시적 요청, 정보 누락, 모델 추론, 고영향 작업을 구분한다. 대량 변경과 되돌릴 수 없는 변경의 판정 기준도 추가한다.
2. S3 분리 및 시험 안전성 확정
   S3a는 실제 destructive 확인 검증, S3b는 REST fallback 검증으로 분리한다. RSBOX 접근 통제도 명시한다.
3. AC-2~AC-4 검증 계약 보완
   확인 요청 → 사용자 응답 → 실제 호출 순서를 검증한다. 확인 거절과 승인 후 정상 실행도 검사한다.
4. D2와 D4의 operation 일치 기준 정리
   커넥터 경로와 REST 경로 각각의 일치 조건을 명시한다. Negative 요청은 잘못된 후보를 제시하지 않고 중단한다.
5. D3·D6·D7 상위 계약 보완
   검수 결과의 상태, 필수 헤더, 출처 불가 상태, 서버 URL·자격증명 생성 금지를 명시한다.
6. S1~S7 시험 입력 고정
   실제 사용자 요청 문장, 예상 도구 호출, 예상 입력값과 합격 조건을 고정한다.

## 6. 최종 결론

이번 v0.2에서 긍정적으로 평가하는 부분은 분명하다.

- 책임 분리 자체가 올바르다.
- 커넥터 검색 실패를 미지원으로 단정하지 않는다.
- REST operation을 무조건 신뢰하지 않는다.
- 실제 REST 전송을 스킬의 책임에서 제외했다.
- 하네스 권한과 사용자 의사 확인을 분리했다.
- Phase 3 게이트 실패를 무시하고 MCP 범위를 확장하지 않았다.

이 결정들은 유지하는 것이 좋겠다.

다만 이번 스펙에서 가장 중요한 설계적 문제는 D5와 AC-2~AC-4가 아직 동일한 안전 정책을 검증하지 못한다는 것이다.

내가 특히 중요하게 보는 것은 다음 세 가지다.

첫째, 사용자의 명시적 요청을 존중하되 모델이 임의로 보충한 값을 사용자의 의사로 간주하지 않아야 한다.

둘째, 실행하지 않아서 안전한 것과 올바른 확인 절차를 거쳐 안전하게 실행한 것을 구분해야 한다.

셋째, 스킬이 잘못 행동해도 실제 데이터가 손상되지 않도록 시험 환경을 격리해야 한다.

이 세 가지는 문서 표현의 문제가 아니라 실제 동작의 정확성과 안전성에 직접 영향을 준다.

따라서 내 최종 추천은 v0.2의 구조와 결정 대부분을 유지하고, 위 필수 지적을 반영한 v0.3을 작성한 뒤 최종 검수하는 것이다.

아직 SKILL.md를 작성하지 않은 것은 좋은 판단이다. 이번 수정은 구현을 시작하기 전에 마무리하는 편이 낫다.
