판정: 재작업

전체적인 방향은 타당하다. 특히 커넥터와 OpenAPI MCP의 역할을 분리하고, 기존 MCP의 범위를 확장하지 않고 Claude Code 스킬 하나로 라우팅을 담당하게 한 결정은 적절하다.

다만 현재 v0.1은 실제 스킬을 작성하기에는 몇 가지 중요한 계약이 열려 있다. 특히 D2의 라우팅 기준, D4의 사용자 확인 정책, REST 경로의 종료 조건은 먼저 확정해야 한다.

이번 검수에서는 설계 방향을 뒤집을 필요는 없다고 판단한다. 기존 D1~D7을 최대한 유지하면서 모호한 부분을 명시하는 방향을 권장한다.

## 1. 필수 지적 사항

### \[필수\] I-01. 커넥터에서 검색되지 않는다는 것과 지원하지 않는다는 것은 다르다

근거: spec §2 D1~D2, §6 Q1 / AGENTS.md §Atlassian APIs

현재 확인된 사실은 다음과 같다.

- 커넥터 카탈로그는 327개다.
- 검색 가능한 항목은 192개다.
- 이슈 삭제는 한 차례 discover 결과에서 나타나지 않았다.
- 전체 커버리지는 확인되지 않았다.

그런데 D2는 다음과 같이 동작한다.

`직접 도구에 없음 → discover → 그래도 없으면 REST`

여기서 문제가 생긴다.

`discover` 결과가 없다는 사실은 해당 기능을 커넥터가 지원하지 않는다는 증거가 아니다. 검색어, 검색 범위, operation 설명의 차이 때문에 누락됐을 가능성이 있다.

따라서 다음 세 가지를 구분해야 한다.

1. 커넥터에 해당 작업을 수행할 도구가 확인됨.
2. 현재 discover 검색에서 적절한 작업을 찾지 못함.
3. 커넥터가 해당 작업을 지원하지 않는다는 사실이 확인됨.

현재 자료로는 2번에서 3번으로 넘어갈 근거가 없다.

내 추천은 다음과 같다.

- 직접 도구가 요청을 충분히 지원하면 직접 도구를 사용한다.
- 직접 도구가 없으면 discover를 사용한다.
- 검색 결과가 불충분하면 제한적으로 검색어를 바꿔 재탐색한다.
- 그래도 찾지 못하면 '커넥터에서 발견되지 않음'으로 판정한다.
- REST 경로로 넘어가더라도 커넥터의 미지원이 확인됐다고 표현하지 않는다.

Q1에서 대표 작업 10여 개를 확인하는 것은 도움이 된다. 다만 그것으로 327개 전체의 커버리지를 증명할 수는 없다.

Q1은 전체 커버리지 확인이 아니라, 검색 실패를 어떻게 취급할 것인지에 대한 정책을 확정하는 방향으로 닫는 것이 좋다.

### \[필수\] I-02. OpenAPI MCP 검색 결과를 자동으로 신뢰해서는 안 된다

근거: spec §3 D2 / docs/phase3-readiness.md Round 5

이 부분은 상위 문서와의 정합성에서 중요한 문제다.

현재 Phase 3 진입 조건은 충족되지 않았다. 특히 Search Quality Round 5의 최종 평가 결과는 다음과 같다.

| 평가 항목 | 결과 | 기준 |
| --- | --- | --- |
| Held-out | 14/16 | 15/16 이상 |
| Negative | 6/8 | 8/8 |
| Discovery Gate | 실패 | 통과 필요 |

실패 사례에는 다음이 포함된다.

- 이슈 첨부파일 삭제 요청에 엉뚱한 GET 요청이 상위에 노출되는 사례
- 존재하지 않는 작업에 대해 DELETE 요청이 상위에 노출되는 사례
- Confluence 페이지 삭제 요청에서 실제 DELETE보다 GET이 상위에 노출되는 사례

이는 단순한 검색 정확도 문제가 아니다. 라우팅 스킬이 잘못된 API 요청 명세를 사용자에게 제시할 가능성이 있다는 뜻이다. 붙여넣은 텍스트(1).txt 붙여넣은 텍스트(1).txt

따라서 D2의 다음 순서는 유지하되, 검색 결과를 확정하는 절차를 추가해야 한다.

`search_operations → get_operation → get_schema → build_request_template → check_request`

중요한 것은 검색 결과의 1위가 아니라 실제 작업 의도와 Operation의 일치 여부다.

최소한 다음을 확인해야 한다.

- 제품 구분(Jira / Confluence)
- HTTP Method
- Endpoint Path
- Operation 설명
- Request Schema
- 실제 요청 의도와의 일치 여부

일치 여부를 확신할 수 없다면 임의로 선택하지 않고 사용자에게 확인해야 한다.

특히 현재 Phase 3 게이트가 실패한 상태에서 검색 결과를 자동으로 신뢰하는 동작은 피해야 한다.

### \[필수\] I-03. D1의 정본 규칙이 직접 도구까지 포괄하는지 불분명하다

근거: spec §3 D1~D2

D1은 다음을 결정했다.

> 커넥터 입력 규격은 discover가 정본이며 스킬이 복제하지 않는다.

그런데 커넥터에는 직접 호출하는 도구도 존재한다.

직접 도구는 discover를 거치지 않을 수 있으므로, 현재 문장만으로는 직접 도구의 입력 규격을 어디에서 가져오는지 명확하지 않다.

다음처럼 범위를 구분하는 것이 좋겠다.

- 직접 도구: 해당 도구가 제공하는 입력 규격을 따른다.
- 동적 발견 도구: discover가 반환하는 입력 규격을 따른다.
- 스킬: 어느 쪽이든 입력 규격을 복제하거나 자체적으로 재정의하지 않는다.

설계 방향을 변경할 사항은 아니다. 정본의 적용 범위만 명확히 하면 된다.

### \[필수\] I-04. D3와 Q3의 종료 조건을 확정해야 한다

근거: spec §3 D3, §6 Q3 / AGENTS.md §Atlassian OpenAPI Intelligence MCP

현재 D3는 올바르다.

REST 경로에서는 요청 명세까지만 만들고 실제 실행은 하지 않는다.

이는 AGENTS.md의 다음 경계와 정확하게 일치한다.

- MCP 서버는 Jira/Confluence API를 호출하지 않는다.
- 서버 URL을 생성하지 않는다.
- 자격증명을 생성하지 않는다.
- Request Template과 구조 검사를 제공한다.

따라서 여기서 새로운 실행 주체를 설계할 필요는 없다. 붙여넣은 텍스트(1).txt

다만 사용자 경험 측면에서 종료 조건이 빠져 있다.

예를 들어 사용자가 다음을 요청했다고 하자.

"Jira 이슈에 첨부파일을 업로드해 줘."

커넥터에서 작업을 발견하지 못해 REST 경로로 진입했다면 스킬은 다음까지만 수행할 수 있다.

1. 적절한 Operation 검색
2. Operation 상세 확인
3. 필요한 Schema 확인
4. Request Template 생성
5. 구조 검사
6. 요청 명세와 검수 결과 반환

이후 실제 업로드는 하지 않는다.

따라서 반드시 다음 의미를 명시해야 한다.

- REST 경로는 요청 명세 산출로 종료한다.
- 실제 요청이 전송되지 않았음을 명확히 알린다.
- 작업이 완료됐다고 표현하지 않는다.

Q3는 별도의 실행 주체를 정의하지 않는 것으로 닫아도 된다. 오히려 이번 스킬의 범위를 유지하는 데 적절하다.

### \[필수\] I-05. D4와 AC-4의 사용자 확인 정책을 재설계해야 한다

근거: spec §3 D4, §5 AC-4, §6 Q2

이번 검수에서 가장 신중하게 다뤄야 할 부분이다.

현재 D4는 쓰기 작업 전 사용자에게 대상과 내용을 보여 주고 확인받도록 한다.

그런데 여기에는 두 가지 서로 다른 권한 개념이 섞여 있다.

| 구분 | 의미 |
| --- | --- |
| 사용자 의사 확인 | 사용자가 실제로 해당 변경을 원한다는 확인 |
| 하네스 권한 승인 | 도구 실행을 허용하는 기술적 권한 확인 |

두 가지는 같은 것이 아니다.

예를 들어 사용자가 이미 "이슈 ABC-123의 담당자를 변경해 줘"라고 요청했다면 작업 의도는 명확하다.

여기서 스킬이 다시 확인을 요구하고, 이후 하네스도 도구 실행 권한을 요청한다면 불필요한 이중 확인이 발생할 수 있다.

반대로 하네스가 단순히 도구 사용만 허용하고 실제 변경 대상이나 내용을 사용자에게 충분히 보여 주지 않는다면, 별도의 의사 확인이 필요할 수 있다.

현재 제공된 AGENTS.md에는 이 권한 프롬프트의 구체적인 작동 방식이 기록되어 있지 않다. 그러므로 중복 여부를 확정할 수는 없다.

내 추천은 다음과 같다.

- 일반적인 생성·수정: 사용자의 명시적인 작업 요청과 하네스 권한 정책을 존중한다. 매번 추가 확인을 요구하지 않는다.
- 삭제·대량 변경 등 영향이 큰 작업: 대상, 범위, 변경 내용과 영향을 보여 주고 명시적으로 확인받는 정책을 검토한다.
- 하네스 권한 승인은 별도의 기술적 통제로 유지한다.
- 스킬은 하네스의 권한 확인을 우회하거나 자동 승인하지 않는다.

다만 최종 정책은 실제 Claude Code의 커넥터 도구 권한 설정을 확인한 뒤 결정해야 한다.

AC-4에도 문제가 있다.

현재 기준은 다음과 같다.

> S3에서 사용자 확인 없이 write/destructive를 실행하는 경우가 0회여야 한다.

이 기준은 스킬 자체의 안전성을 검증하지 못할 수 있다.

예를 들어 스킬이 사용자 확인 없이 도구를 호출했더라도 하네스가 실행을 막았다면 AC-4는 통과할 수 있다.

즉, 하네스가 막은 것인지 스킬이 올바르게 행동한 것인지 구분할 수 없다.

따라서 다음을 구분해서 검증해야 한다.

1. 스킬이 확인 정책을 준수했는가.
2. 하네스가 권한 정책을 준수했는가.

AC-4는 단순히 실행 횟수 0회를 검사하는 대신, 사용자 확인 전에 실제 쓰기 작업이 호출되지 않았는지를 관찰 가능한 도구 호출 기록으로 검증하는 방향이 적절하다.

## 2. 완료 기준(AC) 검토

| 기준 | 판정 | 검토 의견 |
| --- | --- | --- |
| AC-1 RED | 수정 필요 | 시나리오가 추상적이고 관찰 기준이 불명확 |
| AC-2 GREEN | 수정 필요 | D2·D4·D5·D6의 행동별 합격 조건 필요 |
| AC-3 반복 5회 | 권장 | 수동 판정만으로는 재현성과 일관성 부족 |
| AC-4 안전성 | 필수 수정 | 스킬과 하네스의 안전성 검증 분리 |
| AC-5 길이 및 description | 동의 | 단어 수 산정 범위와 형식만 명시 필요 |

### AC-1의 추가 문제

S1은 조회와 생성을 하나의 시나리오로 묶었다.

S3는 삭제와 대량 변경을 하나로 묶었다.

이 둘은 서로 다른 행동이므로 분리하는 것이 좋겠다.

또한 "합리화 문장"이라는 표현은 바꾸는 것이 좋다.

모델의 내부 추론을 그대로 기록하는 것은 검증 가능한 요구사항이 아니다. 대신 다음을 기록하면 된다.

- 사용자에게 표시된 라우팅 판단 설명
- 실제 호출한 도구
- 도구에 전달한 입력
- 최종 응답
- 기대 행동과 실제 행동의 차이

이것이면 라우팅 판단을 충분히 검증할 수 있다.

### AC-3의 추가 문제

5회 반복 자체는 초기 스킬 검증에 사용할 수 있다.

다만 5회 성공을 안전성 보증으로 해석해서는 안 된다.

특히 AC-4처럼 안전성과 관련된 기준은 반복 횟수보다는 도구 호출 이전의 승인 조건을 결정적으로 검증하는 것이 중요하다.

### AC-5

500단어 제한은 좋은 제약이다.

다만 다음을 명시하면 된다.

- 500단어는 SKILL.md 본문 기준인지, frontmatter를 포함하는지
- description은 frontmatter의 description 필드인지
- 자동으로 단어 수를 계산할 것인지

스킬의 핵심이 라우팅인 만큼 불필요하게 긴 지침을 만들지 않는 방향은 유지하는 것이 좋겠다.

### \[권장\] I-06. Provenance의 출처별 상태 표시

D5의 방향은 좋지만, Jira Platform과 Confluence의 freshness가 서로 다를 수 있다.

따라서 단일한 stale 표시보다는 실제 응답에 포함된 source별 provenance를 기준으로 설명하는 것이 안전하다.

또한 stale 상태의 결과를 최신 공식 명세로 표현해서는 안 된다.

### \[권장\] I-07. `get_schema`는 조건부 호출로 명시

현재 D2는 모든 도구를 순서대로 호출하는 것으로 읽힌다.

하지만 모든 요청에서 Schema 조회가 필요한 것은 아니다.

실제 필요한 Request Body나 참조 Schema가 있는 경우에만 `get_schema`를 호출하도록 하는 것이 효율적이다.

이는 Agent Context 절약이라는 기존 MCP 설계 원칙에도 부합한다.

추가로 한 가지 선행 확인이 필요하다.

### \[필수\] I-08. Claude Code에서 커넥터 도구를 실제 사용할 수 있는지 확인

현재 스펙은 `.claude/skills/atlassian-routing/SKILL.md`를 만들면서 claude.ai Atlassian 커넥터를 사용한다는 전제다.

그런데 제공된 자료만으로는 claude.ai에 연결된 커넥터 도구들이 Claude Code 세션에서도 실제로 호출 가능한지 확인되지 않는다.

이건 구현 전에 반드시 확인해야 한다.

스킬이 존재하는 런타임에서 커넥터 도구에 접근할 수 없다면 라우팅 설계 자체가 성립하지 않기 때문이다.

## 5. 최종 수정 우선순위

나는 다음 순서로 진행하는 것을 권장한다.

1. 런타임 접근성 확인
   Claude Code에서 Atlassian 커넥터의 직접 도구와 discover를 실제로 사용할 수 있는지 확인한다.
2. 라우팅 정책 확정
   D1·D2를 보완한다. 직접 도구, discover, REST 명세 생성 사이의 진입 조건과 검색 실패 시 동작을 결정한다.
3. 권한 정책 확정
   D4와 AC-4를 수정한다. 하네스 권한 승인과 사용자 의사 확인의 관계를 정리한다.
4. 종료 조건 확정
   D3를 보완하고 Q3를 종결한다. REST 경로는 명세 생성 후 반드시 종료한다.
5. AC-1~5 수정
   시나리오를 구체화하고 관찰 가능한 합격 기준을 만든다.

## 최종 의견

이 스펙에서 가장 잘한 결정은 기존 Atlassian OpenAPI MCP를 수정하거나 확장하려 하지 않고, 라우팅 책임을 외부 스킬로 분리한 것이다.

이 구조는 유지하는 것이 좋겠다.

다만 나는 이 스킬을 단순히 다음과 같이 생각해서는 안 된다고 본다.

`Connector 우선 → 실패하면 REST`

실제로는 다음과 같은 책임 분리가 더 정확하다.

- Connector: 실제 Jira/Confluence 작업을 수행하는 실행 계층
- OpenAPI MCP: 공식 API 명세를 바탕으로 REST 요청을 설계하고 검수하는 지식 계층
- Routing Skill: 작업의 성격과 도구의 가용성을 판단하고 적절한 계층으로 연결하는 오케스트레이션 계층
- Claude Code Harness: 도구 실행 권한과 승인 통제를 담당하는 실행 환경

이 네 가지 책임이 서로 침범하지 않도록 하는 것이 이번 스킬의 핵심이다.

내 판단은 기존 스펙의 방향을 유지한 채 v0.2로 수정하는 것이다. 특히 D4를 제외한 나머지 결정은 대체로 작은 보완으로 해결할 수 있다. D4만은 실제 하네스 권한 구조를 확인하기 전까지 확정하지 않는 것이 좋겠다.
