# Phase 2.5 — Discovery Hardening — Technical Specification

**문서 버전:** v1.2
**기준일:** 2026-09-30
**선행 구현:** Phase 2 Atlassian OpenAPI Intelligence MCP (spec v2.1, `main` 463abc5, 오프라인 테스트 230개)
**목적:** Phase 3(실제 실행 계층) 진입 조건 중 "discovery가 충분히 안정적", "request template이 실제 API 형태와 일치", "validation이 실사용 수준"을 **독립된 근거**로 충족시킨다.
**설계 원칙:** Evidence-first with frozen evaluation sets / Spec-external knowledge is explicit, attributed and revocable / Optional dependencies stay optional / Registry untouched, policy fingerprinted / No execution

### 0.2 실제 스펙 사실

- `X-Atlassian-Token`은 jira-platform 4개 op(`POST .../issue/{issueIdOrKey}/attachments`, `POST .../issuetype/{id}/avatar2`, `POST .../project/{projectIdOrKey}/avatar2`, `POST .../universal_avatar/type/{type}/owner/{entityId}`)의 description에만 `` `X-Atlassian-Token: no-check` `` 형태로 나타나고 parameter로 선언된 곳은 없다.
- `getIssue`는 jira-platform·jira-software 양쪽에 있다(같은 operationId, 다른 key).
- 세 source 모두 OpenAPI 3.0.x다(3.0.1, 3.0.1, 3.0.3). OAS 3.0 Schema Object는 JSON Schema draft-07이 아니라 Wright Draft 00의 확장 부분집합이다. OAS 3.1의 dialect는 root `jsonSchemaDialect`와 schema의 `$schema`로 정해지는데, Phase 2 registry는 root `jsonSchemaDialect`를 보존하지 않는다.

- 2026-09-29 사용자: 7개 항목 포함, quirks lazy 계산, 로그 opt-in, `jsonschema` 별도 optional.

## 1. 목표

> 식별자 질의는 정확히, 자연어 질의는 **구현 전에 동결된** held-out/negative 벤치마크로 검증된 수준으로 올바른 operation을 찾고, template은 스펙 밖 실행 계약(헤더·multipart)을 출처와 강제 수준을 밝혀 반영하며, `jsonschema`가 있으면 OAS 3.0→draft-07 변환을 거쳐 body 전체를 검증한다. 실행·인증·site URL은 만들지 않는다.

## 2. 범위

### 2.1 포함
1. 식별자 정확 일치 질의 최상위 보장
2. 검색 alias (query→spec 방향 직접 매핑 + 조건부 규칙, 분리된 감쇠)
3. 검색 벤치마크 3종(seed / held_out / negative)과 동결·승격 절차, 진단 스크립트
4. 검색 질의 로그 (opt-in, 로컬)
5. Operation quirks: description mining(advisory) + curated override(required/suppress) + 구조화된 request hints
6. `intelligence_fingerprint`(policy) / `validation_fingerprint`(runtime) 분리
7. `check_request`의 `jsonschema` 경로 — OAS 3.0 전용 transpiler, fallback 사유 열거
8. MCP `body_present`
9. unavailable source refresh 억제
10. 자격증명 헤더: 정적 목록 + securitySchemes(apiKey in header) 동적 확장, redaction, 헤더 상수 단일화
11. status 진단: orphaned override keys, header candidates, validation capabilities
12. 요청 payload fixture(출처 표기)와 Phase 3 재판정 기록

### 2.2 제외
실제 실행, OAuth/토큰, site URL, MCP Resources, embedding, 공식 가이드 문서 인텔리전스, Phase 1 수정, registry/`Operation` 모델/normalizer 변경, alias의 인덱스 측 적용, 자유 형식 description 파싱, 시크릿 탐지기, **OAS 3.1 강한 검증**(dialect 정보를 registry가 보존하지 않으므로 structural fallback; 실제 Atlassian 스펙은 전부 3.0.x라 Phase 3 진입에 영향 없음).

## 3. 설계 원칙
1. **스펙 밖 지식은 명시적·출처 있음·취소 가능.**
2. **Registry는 그대로, policy는 fingerprint.** 정책 영향을 받는 응답(search/template/check/status)에 `intelligence_fingerprint`를 싣는다. runtime 검증 엔진은 별도 `validation_fingerprint`로 구분한다.
3. **Optional은 optional.**
4. **평가의 독립성.** held_out·negative는 구현 시작 전에 동결되고 alias 작성자는 그 결과를 보고 alias를 조정하지 않는다.
5. **관찰값과 계약을 섞지 않는다.**
6. **자격증명 값은 어디에도 다시 나타나지 않는다.**

## 5. 식별자 정확 일치 (`search.py`)

- 적용 조건: `q = query.strip()`에 내부 공백이 없을 때만.
- 1순위: `q`가 `operation_id`와 대소문자 구분 일치, 또는 canonical key와 정확 문자열 일치. 2순위(1순위 없을 때): `q.lower() == operation_id.lower()`.
- 매치 op들은 필터 적용 후 결과 맨 앞에 key 오름차순 고정. `match ∈ {"exact_operation_id","exact_operation_id_ci","exact_key"}`.
- `score`: **필터 적용 후 non-exact lexical 후보의 최대 score(없으면 0) + 1.0**. exact끼리는 score로 순위를 나누지 않는다.
- 응답 `exact_match: bool`.

## 6. 검색 alias (`search.py`, `policy.py`, `data/search_aliases.json`)

### 6.1 데이터 형식과 방향
```json
{
  "version": 1,
  "alias_damping": 0.5,
  "rule_damping": 1.0,
  "aliases": {
    "fetch":  ["get"],
    "read":   ["get"],
    "edit":   ["update"],
    "remove": ["delete"],
    "ticket": ["issue"]
  },
  "rules": [
    {"when_all": ["transition", "issue"], "add": ["transitions", "dotransition"]},
    {"when_all": ["update", "page"],      "add": ["updatepage"]},
    {"when_all": ["issue", "key"],        "add": ["getissue"]}
  ]
}
```
- **방향은 query-token → spec-token.** 사용자가 쓸 법한 단어(`fetch`)를 스펙 어휘(`get`)로 보낸다. 반대 방향은 넣지 않는다.
- `aliases`는 직접 동의어만. 의도 추론(`status→transitions`, `user→assignee`, `content→body`, `list→search`)은 `rules`로만.
- 모든 토큰은 tokenizer 출력 형식(소문자, plural variant 미포함). 로드 시 검증 실패 → `ValueError`.
- 위 seed는 **구현 전에 확정**한다(§7.3 절차). held_out/negative 결과를 보고 고치지 않는다.

### 6.2 평가 순서 (고정, cascade 없음)
```text
base   = tokenize(query)                           # joined form 포함, Phase 2 규칙
direct = ∪ aliases[t] for t in base  − base          # 1회
cond   = ∪ rule.add for rule if rule.when_all ⊆ (base ∪ direct)  − base − direct   # 1회
```
- `cond`의 토큰은 다른 rule의 trigger가 되지 않는다. 재귀 확장 없음.
- `direct`·`cond` 토큰에 plural variant 적용.

### 6.3 점수
`score = Σ_base w·[hit] + alias_damping·Σ_direct w·[hit] + rule_damping·Σ_cond w·[hit]`. all-match 보너스는 `tokenize(query)` 원 토큰만으로 판정(Phase 2 규칙 유지). 두 damping은 데이터 파일 값이며 기본 0.5 / 1.0.

### 6.4 응답 필드
`query_tokens`(base, 정렬), `alias_tokens`(direct ∪ cond, 정렬), `expanded_tokens`(합집합, 정렬).

## 7. 검색 벤치마크 (`tests/benchmarks/search_queries.json`, `tests/diag_search_queries.py`)

### 7.1 레코드 스키마 (세 집합 공통)
```json
{"query": "get issue status", "expected_top1_any": [], "forbidden_top1": ["jira-platform:POST:/rest/api/3/issue/{issueIdOrKey}/transitions", "jira-platform:GET:/rest/api/3/issue/{issueIdOrKey}/transitions"], "note": "..."}
```
- `expected_top1_any`: 1위가 이 중 하나여야 통과(비어 있으면 검사 안 함). `forbidden_top1`: 1위가 이 중 하나면 실패. 둘 중 하나 이상 필수. 같은 evaluator를 세 집합에 재사용.

### 7.2 세 집합
- `seed`: 관찰된 실패 3개 + Phase 2 §13.5 6개. 회귀용, alias 설계에 사용됨. fixture 위 단위 테스트로 고정.
- `held_out`: alias 설계에 쓰지 않은 paraphrase ≥ 12개. 예: `attach a file to a jira ticket`, `change issue assignee`, `post a comment on an issue`, `create a new confluence page in a space`, `fetch page by id`, `run jql query`, `add issue to sprint`, `list boards`, `delete an attachment`, `get project by key`, `update page title`, `move issue to backlog`.
- `negative`: alias가 오답을 올릴 수 있는 질의 ≥ 8개. 예: `get issue status`(전이 API 금지), `get user`, `list users`, `update issue summary`, `get page property`, `get transitions`(→ `getTransitions` 기대).

### 7.3 동결·승격 절차
1. held_out·negative는 **구현 시작 전에 커밋되어 동결**된다. alias/rule 작성은 seed와 실제 operationId 어휘만 보고 한다.
2. 구현 후 진단 스크립트로 1회 평가하고 결과를 `docs/phase3-readiness.md`에 기록(§18).
3. held_out/negative에서 실패가 나오면 그 질의는 **다음 iteration의 seed로 승격**하고, 같은 수의 새 unseen 질의를 held_out에 추가한 뒤 재평가한다. 실패를 본 뒤 alias를 고치고 같은 held_out으로 다시 재는 것은 금지다.
4. 진단 출력에는 집합별 정답률, 오답 목록, `registry_fingerprint`, `intelligence_fingerprint`, source별 spec sha, 실행일을 포함한다.

실행: 수동, 실제 캐시, `sync_all` no-op 주입, 네트워크 없음.

## 9. Operation quirks (`quirks.py`, `data/operation_quirks.json`)

### 9.1 모델
```python
@dataclass(frozen=True)
class HeaderQuirk:
    name: str             # 표시용 원문
    value: str | None
    enforcement: str      # "advisory" | "required"
    value_policy: str     # "observed" | "literal"
    origin: str           # "quirk:description" | "quirk:override"
    note: str | None

@dataclass(frozen=True)
class MultipartField:
    name: str; required: bool; kind: str; note: str | None    # kind: "file" | "text"

@dataclass(frozen=True)
class OperationQuirks:
    key: str
    headers: tuple[HeaderQuirk, ...]
    request_hints: dict           # {"multipart_fields": [...]} 등 구조화된 것만
    notes: tuple[str, ...]
    suppressed: tuple[str, ...]
```
헤더 identity는 항상 `name.lower()`로 비교한다.

### 9.2 Description mining (advisory only)
- `MINED_HEADERS = ("X-Atlassian-Token",)`. 규칙: `` `?(X-Atlassian-Token)\s*:\s*([A-Za-z0-9_-]+)`? `` → `HeaderQuirk(enforcement="advisory", value_policy="observed", origin="quirk:description")`. 값 없는 언급은 §9.5 candidate scan만.
- mining만으로는 error·`missing_required`가 생기지 않는다.

### 9.3 Curated override
```json
{"version": 1, "operations": {
  "jira-platform:POST:/rest/api/3/issue/{issueIdOrKey}/attachments": {
    "headers": [{"name": "X-Atlassian-Token", "action": "set", "value": "no-check", "enforcement": "required", "value_policy": "literal", "note": "Atlassian docs: XSRF bypass required for multipart uploads"}],
    "request_hints": {"multipart_fields": [{"name": "file", "required": true, "kind": "file"}]},
    "notes": []}}}
```
- 키는 canonical key 전체 일치만. `action ∈ {"set","suppress"}`.
- 같은 정규화 헤더에 대해 override entry가 2개 이상이거나 `set`과 `suppress`가 함께 있으면 loader가 `ValueError`로 거부.
- `set`은 같은 이름의 mined header를 대체한다. `suppress`는 mined header를 제거하고 `suppressed`에 기록.
- 조합 계약(loader는 네 조합 모두 허용):

| enforcement / value_policy | 누락 | 값 불일치 |
|---|---|---|
| advisory / observed | warning `advisory_header_missing` | warning `quirk_value_mismatch` |
| required / observed | error `required` | warning `quirk_value_mismatch` |
| advisory / literal | warning `advisory_header_missing` | error `quirk_value_mismatch` |
| required / literal | error `required` | error `quirk_value_mismatch` |

- mining은 항상 advisory/observed. 초기 seed: 관찰된 4개 op 모두 required/literal `no-check`, attachments에 `multipart_fields`.

### 9.4 계산 시점
`quirks.for_operation(op) -> OperationQuirks` lazy. registry 불변.

### 9.5 진단 (status `diagnostics`)
- `orphaned_override_keys`: active registry에 없는 override 키.
- `header_candidates`: 허용 목록 밖 `X-[A-Za-z0-9-]+` 언급 `{key, header}` 목록(자동 적용 없음).

### 9.6 template 반영
- 헤더 항목: `{"declared_required", "effective_required", "value", "origins": [...], "effective_required_origins": [...], "enforcement", "note"}`. `effective_required = declared_required OR quirk.enforcement == "required"`; `effective_required_origins`는 그 원천 전부(`"spec"`, `"quirk:override"`, ...).
- `missing_required`는 `effective_required`이고 값 없는 헤더 포함. advisory 누락은 `advisories`에만.
- `request_hints` 그대로 출력. 최상위 `quirks: {applied, advisories, suppressed, request_hints}`.

### 9.7 check 반영
§9.3 표대로 error/warning. multipart hint의 required field가 dict body에 없으면 warning `multipart_field_missing`. `checked`에 `quirk_headers`.

## 10. Fingerprint와 policy provenance (`policy.py`)

- 데이터 파일 hash: `sha256(json.dumps(parsed, sort_keys=True, separators=(",", ":"), ensure_ascii=False).encode("utf-8"))` (canonical JSON; whitespace 변경은 hash를 바꾸지 않는다).
- `POLICY_VERSIONS = {"search": 2, "quirks": 1, "oas_transpiler": 1}`. **bump 규칙:** search 점수/토큰화, quirks mining/적용, transpiler의 관찰 가능한 의미가 바뀌면 해당 버전을 반드시 올린다. 구현 계획과 리뷰 체크리스트에 항목으로 둔다.
- `intelligence_fingerprint = sha256(registry_fingerprint + "\n" + aliases_sha256 + "\n" + overrides_sha256 + "\n" + canonical(POLICY_VERSIONS))` — policy 재현성만 나타낸다.
- `validation_fingerprint = sha256(intelligence_fingerprint + "\n" + engine + "\n" + jsonschema_version + "\n" + transpiler_version)` — `check_request` 응답에만.
- policy-sensitive 응답(search/template/check/status)에 `intelligence_fingerprint`와 `intelligence_policy: {aliases_sha256, overrides_sha256, versions}`. `get_operation`/`get_schema`는 대상이 아니다.

## 11. `jsonschema` 경로 (`oas_schema.py`, `request_check.py`)

### 11.1 의존성과 경계
- `requirements-validate.txt`: `jsonschema>=4.18,<5`.
- `oas_schema.py`는 **stdlib만** 쓰는 순수 변환 모듈이며 항상 테스트된다. `jsonschema`는 `request_check.py`에서만 `find_spec` 확인 후 함수 안에서 import한다. layering test는 `request_check.py`의 guarded import만 허용.
- 버전 조회는 `importlib.metadata.version("jsonschema")`(installed distribution version).

### 11.2 `oas30_to_draft7(schema) -> TranspiledSchema` (request 방향)
```python
@dataclass(frozen=True)
class TranspiledSchema:
    schema: dict
    readonly_paths: tuple[tuple[str, ...], ...]   # ("fields","id"), ("items",) 세그먼트는 배열 원소를 뜻함
```
schema-bearing 키워드(`properties`, `items`, `additionalProperties`(dict), `allOf/oneOf/anyOf`, `not`)만 재귀. 각 노드에서:
1. `nullable is True and isinstance(type, str)` → `type = [type, "null"]`; 그 외에는 `nullable`만 제거(null 허용 추가 없음; allOf 부모 type 상속에 적용 금지).
2. `exclusiveMinimum is True` → `exclusiveMinimum = minimum`, `minimum` 제거; `False`면 키 제거. `exclusiveMaximum` 동일. `minimum`이 없으면 키만 제거.
3. `readOnly is True`인 property는 부모 `required`에서 제거하고 그 경로를 `readonly_paths`에 기록(스키마 안에 marker를 남기지 않는다). `writeOnly`는 required 유지, 키 제거.
4. OAS 전용 키 제거: `discriminator`, `xml`, `externalDocs`, `deprecated`, 모든 `x-*`.

### 11.3 경로 선택과 fallback 사유
```text
body 있음 and body_schema 있음
  ├─ source openapi_version이 "3.0."으로 시작하지 않음 → structural ("oas31_not_supported")
  ├─ jsonschema 없음 → structural ("jsonschema_not_installed")
  ├─ resolved = schemas.resolve(body_schema, comps, max_depth=8, max_nodes=2000); 마커 있음 → structural ("schema_not_fully_resolvable")
  ├─ oas30_to_draft7 실패(ValueError) → structural ("schema_transpile_failed")
  ├─ Draft7Validator.check_schema 실패(SchemaError) → structural ("jsonschema_schema_error")
  ├─ 검증 중 jsonschema.exceptions.SchemaError 또는 referencing.exceptions.Unresolvable → structural ("jsonschema_runtime_error")
  └─ 성공 → "jsonschema"
```
그 밖의 예외는 삼키지 않는다. 응답: `body_check`, `body_check_reason`, `validation_fingerprint`, `validation_engine: {engine, version, transpiler_version}`.

### 11.4 검증과 오류 매핑
- `Draft7Validator(transpiled.schema)` (format checker 없음). `iter_errors` 결과를 `{"location": "body" + path, "rule": f"schema:{validator}", "message"}`로, 최대 50개(초과 시 warning `errors_truncated`). path 표기 `.name` / `[i]`.
- `readonly_paths`에 해당하는 값이 body에 존재하면 warning `readonly_property_present`(경로 tuple을 body에 대해 순회하며 `("items",)` 세그먼트는 배열 각 원소).
- jsonschema 경로 `checked = ["required","type","enum","body_required","content_type","body_not_declared","quirk_headers","jsonschema:body"]`, `not_checked = ["format","cookie parameters"]`. structural 경로는 Phase 2 목록. `compatible = len(errors)==0`, `valid` 키 없음.

### 11.5 capabilities
`get_api_status.capabilities.validation = {"engine": "jsonschema"|"structural", "version": <installed version|None>, "oas_transpiler_version": 1, "oas31_strong_validation": false}`.

## 12. MCP `body_present`
`check_request` tool에 `body_present: Optional[bool] = None`. `False` → `MISSING`(body가 None이 아니면 warning `body_ignored`); `True` → `body`(None이면 명시적 null); `None` → Phase 2 동작. description에 명시.

## 13. unavailable source refresh 억제 (`manager.py`)
`needs_refresh(source)`: registry에 없어도 `_rejected[source]`가 있고 `observed_cache_sha256 == _rejected[source]["sha256"] == metadata.sha256`이며 `last_checked`가 TTL 이내면 `False`. 테스트: 거부 캐시만 있는 상태에서 `ensure_fresh()` 5회 → sync 0회, `metadata.json` mtime 불변; TTL 경과 후 1회.

## 14. 헤더 상수·자격증명·redaction (`headers.py`)

```python
TRANSPORT_HEADERS = frozenset({"content-type","accept","content-length","host","user-agent","accept-encoding"})
CREDENTIAL_HEADERS = frozenset({"authorization","proxy-authorization","cookie","set-cookie","x-api-key","x-auth-token"})
REDACTED = "[REDACTED]"
def credential_header_names(source_registry: SourceRegistry) -> frozenset[str]:
    """정적 목록 ∪ source_registry.security_schemes 중 type=apiKey, in=header 인 name(소문자)."""
```
- template/check는 `credential_header_names(source_registry)`를 쓴다. `X-Atlassian-Token`은 포함하지 않는다.
- **Redaction 의미:** 자격증명 헤더의 값은 template/check 결과에 `REDACTED`로만 나타나거나 생략된다; 그 헤더에 관한 error/warning message는 입력값을 포맷하지 않는다; 검색 로그는 헤더를 받지 않는다. MCP 계층의 `internal_error` message는 `f"{type(exc).__name__}"`와 고정 안내문만 담고 `str(exc)`를 포함하지 않는다(Phase 2 정책 변경; 상세는 서버 stderr 로그로).
- 정의는 저장소에서 `headers.py` 한 곳(AST로 할당문 위치 검사).
