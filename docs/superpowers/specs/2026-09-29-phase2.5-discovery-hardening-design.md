# Phase 2.5 — Discovery Hardening — Technical Specification

**문서 버전:** v1.0
**기준일:** 2026-09-29
**선행 구현:** Phase 2 Atlassian OpenAPI Intelligence MCP (spec v2.1, `main` 463abc5, 오프라인 테스트 230개)
**목적:** Phase 3(실제 실행 계층) 진입 조건 중 "discovery가 충분히 안정적", "request template이 실제 API 형태와 일치", "validation이 실사용 수준"을 근거로 충족시킨다.

### 0.2 실제 스펙 사실 (설계 근거)

- `X-Atlassian-Token`은 jira-platform 4개 op의 description에만 나타난다: `POST .../issue/{issueIdOrKey}/attachments`, `POST .../issuetype/{id}/avatar2`, `POST .../project/{projectIdOrKey}/avatar2`, `POST .../universal_avatar/type/{type}/owner/{entityId}`. 문구는 항상 `` `X-Atlassian-Token: no-check` ``. parameter로 선언된 곳은 0개. `X-ExperimentalApi`, `X-Force-Accept-Language`는 어디에도 없다.
- `getIssue`는 jira-platform과 jira-software 양쪽에 존재한다(같은 operationId, 다른 key). 정확 일치 규칙은 중복을 다뤄야 한다.
- 전이 관련 op: `getTransitions`, `doTransition`, `getAvailableTransitions`. 페이지 갱신: `updatePage`, `updatePageTitle`. 배정: `assignIssue`. 댓글: `addComment`.
- Phase 2 최종 리뷰의 deferred 항목 중 이번에 처리하는 것: 정확 operationId 질의 순위, unavailable source의 매 호출 refresh, `TRANSPORT_HEADERS` 중복 정의, 자격증명 헤더 목록.

### 0.3 사용자 결정 (2026-09-29)

포함 7개 항목: 검색 alias + 실패 질의 로그, operation quirks 계층, `jsonschema` 보강, MCP `body_present`, 정확 operationId 최상위 보장, unavailable source refresh 억제, 자격증명 헤더 확장. quirks는 lazy 계산, 검색 로그는 opt-in 환경변수, `jsonschema`는 MCP와 별도 optional 파일.

## 1. 목표

> 자연어·식별자 질의에서 올바른 operation이 1위로 나오고, template이 스펙 밖 필수 헤더까지 출처를 밝혀 반영하며, `jsonschema`가 있으면 body 전체를 검증한다. 실행·인증·site URL은 여전히 만들지 않는다.

## 2. 범위

### 2.1 포함
1. 정확 operationId/key 질의 최상위 보장
2. 검색 alias 테이블 (질의 확장, 데이터 파일)
3. 검색 질의 로그 (opt-in, 로컬 jsonl)
4. Operation quirks 계층 (description mining + curated override), template/check 반영, 출처 표시
5. `check_request` `jsonschema` 보강 (optional dependency, fallback 유지)
6. MCP `check_request`에 `body_present` 인자
7. unavailable source의 매 호출 refresh 억제
8. 자격증명 헤더 목록 확장 + 헤더 상수 단일화
9. 진단 스크립트: 고정 질의 13개의 1위 정답률 출력

### 2.2 제외
실제 실행, OAuth/토큰, site URL, MCP Resources, embedding, 공식 가이드 문서(ADF·pagination·auth) 인텔리전스, Phase 1 수정, registry/`Operation` 모델 변경, alias의 인덱스 측 적용, 자유 형식 description 파싱.

## 3. 설계 원칙
1. **스펙 밖 지식은 명시적이고 출처가 있다.** quirk는 `origin`을 달고 나가며 데이터 파일 sha가 provenance에 실린다.
2. **Registry는 그대로.** 이번 Phase는 registry·모델·normalizer를 바꾸지 않는다. 모든 추가는 질의 시점(lazy)에 계산한다.
3. **Optional은 optional.** `jsonschema` 없이도 Phase 2와 동일하게 동작한다. 있으면 더 강하게 검사하고 어느 경로였는지 말한다.
4. **로그는 opt-in, 로컬, 검색 질의만.** body·header·token은 절대 기록하지 않는다.
5. **근거 없는 동의어는 넣지 않는다.** alias seed는 관찰된 실패 질의와 실제 operationId 어휘에서만 만든다.

## 5. 정확 operationId/key 질의 (`search.py`)

- `norm = re.sub(r"\s+", "", query).lower()`.
- `norm`이 어떤 op의 `operation_id.lower()` 또는 `key.lower()`와 같으면 그 op들을 결과 맨 앞에 고정한다. 여러 개(중복 operationId, 예: `getIssue` ×2)면 key 오름차순.
- 고정된 항목은 `"match": "exact_operation_id"` 또는 `"exact_key"`를 갖고, `score`는 나머지 최고 점수보다 큰 값(`max_score + 1.0`)으로 보고한다. 나머지는 기존 lexical 순서.
- 필터(`source`, `method`, `tag`, `include_deprecated`)는 고정 항목에도 적용된다.
- 고정이 일어나면 응답에 `"exact_match": true`.

## 6. 검색 alias (`search.py`, `data/search_aliases.json`)

### 6.1 데이터 형식
```json
{
  "version": 1,
  "aliases": {
    "transition": ["transitions"],
    "status":     ["transitions"],
    "update":     ["edit", "put"],
    "content":    ["body"],
    "get":        ["fetch", "read"],
    "user":       ["assignee"],
    "assign":     ["assignee"],
    "comment":    ["comments"],
    "delete":     ["remove"],
    "list":       ["search", "all"],
    "key":        ["id"]
  }
}
```
키와 값은 §13.1 tokenizer가 만드는 소문자 토큰이어야 한다(로드 시 검증, 아니면 `ValueError`). 값에 나온 토큰은 §13.1의 plural variant 규칙을 다시 거친다.

### 6.2 적용
- `_query_tokens(query)`가 반환하는 집합을 `base`라 할 때, `expanded = base ∪ {alias for t in base for alias in ALIASES.get(t, ())}`.
- 점수 계산은 `expanded`로 한다. **all-match 보너스는 `tokenize(query)`(원 토큰)만으로 판정**한다(이미 joined 토큰이 그렇듯 확장 토큰은 보너스 조건에서 제외).
- 확장 토큰은 원 토큰과 같은 가중치. 별도 감쇠는 두지 않는다(seed가 작고 검증됐으므로). 관찰 후 필요하면 v2에서 감쇠 도입.
- 응답에 `"expanded_tokens": [...]`(정렬)를 포함해 Agent가 왜 그 결과가 나왔는지 알 수 있게 한다.

### 6.3 seed 고정 테스트
- `transition issue status` → 1위가 `doTransition` 또는 `getTransitions` (둘 중 하나, 둘 다 상위 2개 안).
- `update page content` → 1위 `updatePage`.
- `get issue by key` → 1위 `getIssue`(jira-platform).
- `createIssue` → 1위 `createIssue` (`match: exact_operation_id`).
- `getIssue` → 상위 2개가 `jira-platform:GET:/rest/api/3/issue/{issueIdOrKey}`와 jira-software의 `getIssue`, key 순.
- Phase 2 §13.5의 순위 테스트 6개는 그대로 통과한다(회귀 방지).

## 7. 검색 질의 로그 (`search_log.py`)

- 활성 조건: 환경변수 `ATLASSIAN_DOCS_SEARCH_LOG`가 `1`/`true`/`yes`(대소문자 무시). 기본 꺼짐.
- 경로: `storage.CACHE_DIR / "intelligence" / "search_log.jsonl"` (호출 시점에 계산).
- 레코드: `{"ts": ISO UTC, "query": str, "filters": {"source","method","tag","include_deprecated","limit"}, "expanded_tokens": [...], "exact_match": bool, "total_matches": int, "top": [{"key","score"} ×≤3]}`.
- 기록 실패(OSError)는 삼키고 검색 결과에 영향을 주지 않는다. 검색 응답에도 로그 여부를 표시하지 않는다.
- 회전: 기록 직전 파일 크기가 5 MiB 이상이면 `search_log.jsonl.prev`로 `os.replace`(이전 `.prev`는 덮어씀) 후 새 파일.
- `search_operations`가 아닌 어떤 tool도 이 로그를 쓰지 않는다. `get_api_status.refresh`에 `"search_log_enabled": bool`을 추가한다.

## 8. Operation quirks (`quirks.py`, `data/operation_quirks.json`)

### 8.1 모델
```python
@dataclass(frozen=True)
class HeaderQuirk:
    name: str            # 원문 대소문자 유지, 비교는 소문자
    value: str | None    # 관찰된 값 리터럴 ("no-check"), 없으면 None
    origin: str          # "quirk:description" | "quirk:override"
    note: str | None

@dataclass(frozen=True)
class OperationQuirks:
    key: str
    required_headers: tuple[HeaderQuirk, ...]
    notes: tuple[str, ...]
    overrides_sha256: str | None
```

### 8.2 Description mining
- 허용 목록 `MINED_HEADERS = ("X-Atlassian-Token",)`. 자유 형식 파싱은 하지 않는다.
- 규칙: description에 정규식 `` `?(X-Atlassian-Token)\s*:\s*([A-Za-z0-9_-]+)`? ``가 매치되면 `HeaderQuirk(name, value, "quirk:description")`. 값이 없으면 `value=None`.
- 관찰된 4개 op에서 값은 항상 `no-check`. 다른 값이 나오면 그대로 보존한다(추측하지 않음).

### 8.3 Curated override (`data/operation_quirks.json`)
```json
{
  "version": 1,
  "operations": {
    "jira-platform:POST:/rest/api/3/issue/{issueIdOrKey}/attachments": {
      "required_headers": [{"name": "X-Atlassian-Token", "value": "no-check", "note": "XSRF check bypass for multipart uploads"}],
      "notes": ["multipart/form-data; field name is `file`"]
    }
  }
}
```
- 키는 canonical key 전체 일치만 지원한다(패턴·glob 없음).
- 같은 헤더가 mining과 override 양쪽에서 나오면 override가 이긴다(`origin: "quirk:override"`).
- 로드 시 스키마 검증(키 형식 `{source}:{METHOD}:{path}`, 필드 타입). 실패하면 `ValueError`로 즉시 드러낸다(startup 시 import 단계에서 발견되도록 모듈 로드 시 1회 검증).
- `overrides_sha256 = sha256(파일 canonical JSON)`; 파일이 없으면 `None`.
- 초기 seed: attachments 1건만 override로 두고(설명용), 나머지 3개 avatar op는 mining으로 잡히는지 테스트로 확인한다.

### 8.4 계산 시점
`quirks.for_operation(op) -> OperationQuirks`를 `build_request_template`와 `check_request`가 호출한다. registry·normalizer·모델은 변경하지 않는다. 결과는 `functools.lru_cache(maxsize=4096)`로 (key, description hash) 기준 캐시해도 되나 필수는 아니다.

### 8.5 template 반영 (`request_template.py`)
- `headers[name] = {"required": true, "value": <value|None>, "origin": "quirk:description"|"quirk:override", "note": ...}` — 스펙 선언 헤더는 `"origin": "spec"`을 갖는다(신규 필드).
- 스펙 선언 헤더와 quirk 헤더 이름이 겹치면 스펙 항목을 유지하고 `origin: "spec"`에 `"quirk_value": ...`를 덧붙인다.
- 값이 `values.headers`에 오면 `value`를 그 값으로 덮는다(대소문자 무시 매칭).
- quirk 필수 헤더가 값 없이 남으면 `missing_required`에 이름을 넣는다.
- 응답 최상위에 `"quirks": {"applied": [{"name","origin"}...], "notes": [...], "overrides_sha256": ...}`.

### 8.6 check 반영 (`request_check.py`)
- quirk 필수 헤더가 없으면 `{"location": "header.X-Atlassian-Token", "rule": "required", "origin": "quirk:description", "message": ...}` error.
- 값이 quirk의 `value`와 다르면 warning `{"rule": "quirk_value_mismatch", ...}` (error 아님 — 값은 관찰값이지 계약이 아니다).
- `checked`에 `quirk_headers` 추가. 응답에 `"quirks"` 블록(§8.5와 동일).

## 9. `check_request` jsonschema 보강 (`request_check.py`)

### 9.1 의존성
- `requirements-validate.txt`: `jsonschema>=4.18,<5`. 설치는 선택.
- `request_check.py`는 모듈 상단에서 `jsonschema`를 import하지 않는다. `importlib.util.find_spec("jsonschema")`로 확인 후 함수 안에서 import한다. `tests/test_layering.py`는 `intelligence/request_check.py`에 한해 `jsonschema` import를 허용한다(다른 파일에서 나오면 실패).

### 9.2 경로 선택
```text
body 주어짐 and body_schema 있음
  ├─ jsonschema 사용 가능?
  │    ├─ 예 → resolved = schemas.resolve(body_schema, comps, max_depth=8, max_nodes=2000)
  │    │        ├─ resolved.unresolved/cycles/truncated 중 하나라도 있음 → structural (이유: "schema_not_fully_resolvable")
  │    │        └─ 아니면 → jsonschema 검증
  │    └─ 아니오 → structural (이유: "jsonschema_not_installed")
  └─ 결과에 "body_check": "jsonschema" | "structural", "body_check_reason": str|None
```

### 9.3 jsonschema 검증 규칙
- 전처리: OpenAPI 3.0 `nullable: true` → `type`에 `"null"` 추가(문자열 type이면 `[type, "null"]`), `nullable` 키 제거. `example`은 이미 없다. `discriminator`, `readOnly`, `writeOnly`, `xml`, `externalDocs`는 제거(검증 무관).
- validator: `jsonschema.Draft202012Validator`를 기본으로 하되 `openapi_version`이 `3.0.`으로 시작하면 `Draft7Validator`(3.0은 JSON Schema draft-07 부분집합에 가깝다). `format`은 검사하지 않는다(format checker 미지정).
- 오류 매핑: 각 `ValidationError`를 `{"location": "body" + "".join(f".{p}" if isinstance(p, str) else f"[{p}]" for p in error.absolute_path), "rule": f"schema:{error.validator}", "message": error.message}`로. 최대 50개까지, 초과 시 warning `errors_truncated`.
- `checked`는 `["required","type","enum","body_required","content_type","body_not_declared","quirk_headers","jsonschema:body"]`, `not_checked`는 `["format", "cookie parameters"]`로 바뀐다. structural 경로는 Phase 2 목록 유지.
- parameter 검사(`required/type/enum/unknown_parameter`)는 두 경로 모두 Phase 2 규칙 그대로.
- `compatible = len(errors) == 0`. `valid` 키 없음(불변).

### 9.4 테스트
- `tests/intelligence/test_request_check_jsonschema.py`: `skipUnless(find_spec("jsonschema"))`. createIssue body의 `fields.project`가 문자열일 때 `schema:type` error at `body.fields.project`; 정상 body 통과; `nullable` 필드에 `null` 허용; 순환 schema(`Node`)는 structural로 fallback하고 `body_check_reason == "schema_not_fully_resolvable"`.
- jsonschema 없는 기본 suite에서 structural 경로 테스트는 전부 그대로 통과한다.

## 10. MCP `body_present` (`mcp/tools.py`, `mcp/server.py`)

- `check_request` tool에 `body_present: Optional[bool] = None` 추가.
- `run_tool` 매핑: `body_present is False` → `MISSING`(body 인자 무시); `body_present is True` → `body`(None이면 명시적 null); `None` → Phase 2 동작(`"body"` 키 부재 → MISSING, `null` → 서버 바인딩 한계로 생략 취급).
- tool description: "body를 보내지 않는 경우와 JSON null을 보내는 경우를 구분하려면 body_present를 명시하세요."
- 테스트: `body_present=True, body=None` → `body_root_type`(Strict); `body_present=False, body={...}` → `body_required`.

## 11. unavailable source refresh 억제 (`manager.py`)

- `needs_refresh(source)` 규칙에 다음 예외를 추가한다: source가 registry에 없더라도, `_rejected[source]`가 있고 `observed_cache_sha256 == _rejected[source]["sha256"] == metadata.sha256`이며 `last_checked`가 TTL 이내면 `False`.
- 효과: gate에 거부된 캐시만 있는 source가 매 tool 호출마다 디스크 sync+rebuild+`metadata.json` 재작성을 유발하지 않는다. TTL이 지나면 다시 시도한다(새 upstream 스펙을 받을 기회).
- 테스트: 거부 캐시만 있는 상태에서 `ensure_fresh()` 5회 → sync 0회, `metadata.json` mtime 불변; clock을 TTL 너머로 옮기면 1회.

## 12. 헤더 상수 단일화·확장 (`headers.py`)

```python
TRANSPORT_HEADERS = frozenset({"content-type", "accept", "content-length", "host", "user-agent", "accept-encoding"})
CREDENTIAL_HEADERS = frozenset({"authorization", "proxy-authorization", "cookie", "set-cookie", "x-api-key", "x-auth-token"})
```
- `request_template.py`, `request_check.py`는 여기서 import한다(중복 정의 제거). `X-Atlassian-Token`은 자격증명이 아니므로 포함하지 않는다.
- 테스트: `Proxy-Authorization`, `X-Api-Key` 값이 template/check 어느 출력에도 나타나지 않는다(`credential_header_dropped`/`credential_header_ignored`).

## 13. 진단 스크립트 (`tests/diag_search_queries.py`)

- 수동 실행, 네트워크 없음(`sync_all`을 no-op으로 주입). 고정 질의 13개(§0.1)를 돌려 `기대 op / 실제 1위 / 상위 3` 표와 정답률을 출력한다. 정답률은 gate가 아니라 관찰용이며, 로그 파일이 있으면 그 질의들도 함께 재생해 상위 3을 보여준다.
