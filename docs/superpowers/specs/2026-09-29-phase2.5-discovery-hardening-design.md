# Phase 2.5 — Discovery Hardening — Technical Specification

**문서 버전:** v1.1
**기준일:** 2026-09-29
**선행 구현:** Phase 2 Atlassian OpenAPI Intelligence MCP (spec v2.1, `main` 463abc5, 오프라인 테스트 230개)
**목적:** Phase 3(실제 실행 계층) 진입 조건 중 "discovery가 충분히 안정적", "request template이 실제 API 형태와 일치", "validation이 실사용 수준"을 **독립된 근거**로 충족시킨다.
**설계 원칙:** Evidence-first / Spec-external knowledge is explicit, attributed and revocable / Optional dependencies stay optional / Registry untouched, policy fingerprinted / No execution

## 0. 배경

### 0.1 Phase 3 진입 조건 점검 결과 (2026-09-29, 실제 캐시 942 operations)

| 조건 | 상태 | 관찰 |
|---|---|---|
| discovery 안정성 | 부분 | 자연어 질의 13개 중 10개 1위 정답. 실패: `transition issue status`, `update page content`, `get issue by key`. 정확한 operationId `createIssue`를 그대로 넣어도 3위. |
| template ↔ 실제 API | 부분 | `addAttachment` 등 4개 op는 `X-Atlassian-Token: no-check`가 필수인데 OpenAPI가 description에만 적음. multipart field 이름(`file`)도 스펙에 없음. |
| validation | lint 수준 | depth 2 밖 중첩 구조 미검사. |
| self-update 안정성 | 테스트만 | 실제 upstream 변경 미경험. |
| MCP interface | 충족 | body `null`/생략 구분 불가 wart. |
| major version 대응 | 구조적 | 실증 없음. |

### 0.2 실제 스펙 사실

- `X-Atlassian-Token`은 jira-platform 4개 op(`POST .../issue/{issueIdOrKey}/attachments`, `POST .../issuetype/{id}/avatar2`, `POST .../project/{projectIdOrKey}/avatar2`, `POST .../universal_avatar/type/{type}/owner/{entityId}`)의 description에만 `` `X-Atlassian-Token: no-check` `` 형태로 나타나고 parameter로 선언된 곳은 없다. `X-ExperimentalApi`, `X-Force-Accept-Language`는 등장하지 않는다.
- `getIssue`는 jira-platform·jira-software 양쪽에 있다(같은 operationId, 다른 key).
- 세 source 모두 OpenAPI 3.0.x다(3.0.1, 3.0.1, 3.0.3). OAS 3.0 Schema Object는 JSON Schema draft-07이 아니라 Wright Draft 00의 확장 부분집합이며, `nullable`, boolean `exclusiveMinimum/Maximum`, `readOnly/writeOnly` 의미가 다르다.

### 0.3 결정 이력

- 2026-09-29 사용자: 7개 항목 포함(§2.1), quirks lazy 계산, 로그 opt-in, `jsonschema` 별도 optional.
- 2026-09-29 외부 검수(v1.0 → v1.1): 검색 과적합/순환 증명, exact match 과잉, alias 오염, quirks "언급=필수" 승격, suppress 부재, spec/quirk 충돌, multipart hint 비구조화, policy fingerprint 부재, OAS 3.0→JSON Schema 변환 누락, nullable/readOnly 규칙, fallback 조건, `body_present` 모순 입력, 자격증명 헤더 동적 확장, AC 검증법, Phase 3 재판정 기준 — 전부 반영.

## 1. 목표

> 식별자 질의는 정확히, 자연어 질의는 held-out 벤치마크로 검증된 수준으로 올바른 operation을 찾고, template은 스펙 밖 실행 계약(헤더·multipart)을 출처와 강제 수준을 밝혀 반영하며, `jsonschema`가 있으면 OAS→JSON Schema 변환을 거쳐 body 전체를 검증한다. 실행·인증·site URL은 만들지 않는다.

## 2. 범위

### 2.1 포함
1. 식별자 정확 일치 질의 최상위 보장

4. 검색 질의 로그 (opt-in, 로컬)
5. Operation quirks: description mining(advisory) + curated override(required/suppress) + 구조화된 request hints(multipart)
6. `intelligence_fingerprint`와 policy provenance
7. `check_request`의 `jsonschema` 경로 (OAS 3.0 transpiler, dialect 선택, fallback 사유)
8. MCP `body_present`
9. unavailable source refresh 억제
10. 자격증명 헤더: 정적 목록 + securitySchemes(apiKey in header) 동적 확장, 헤더 상수 단일화
11. status 진단: orphaned override keys, header candidate scan, validation capabilities

### 2.2 제외
실제 실행, OAuth/토큰, site URL, MCP Resources, embedding, 공식 가이드 문서 인텔리전스, Phase 1 수정, registry/`Operation` 모델/normalizer 변경, alias의 인덱스 측 적용, 자유 형식 description 파싱, 시크릿 탐지기.

## 3. 설계 원칙
1. **스펙 밖 지식은 명시적·출처 있음·취소 가능.** 모든 quirk는 `origin`과 `enforcement`를 달고 나가고, curated 파일로 자동 추출을 억제(suppress)할 수 있다.
2. **Registry는 그대로, policy는 fingerprint.** registry·모델·normalizer는 손대지 않는다. 대신 alias·quirk·정책 버전을 합친 `intelligence_fingerprint`가 모든 응답에 실려 재현성을 보장한다.
3. **Optional은 optional.** `jsonschema` 없이 Phase 2와 동일하게 동작한다.
4. **증명의 독립성.** alias 설계에 쓴 질의로 검색 안정성을 증명하지 않는다.
5. **관찰값과 계약을 섞지 않는다.** mining으로 얻은 값은 advisory, 사람이 확정한 값만 required/literal.

## 5. 식별자 정확 일치 (`search.py`)

- 적용 조건: `q = query.strip()`에 **내부 공백이 없을 때만**. `"get issue"`는 lexical 경로로 간다.
- 1순위: `q`가 어떤 op의 `operation_id`와 **대소문자 구분** 일치, 또는 canonical key와 정확 문자열 일치.
- 2순위(1순위 매치 없을 때): `q.lower()`가 `operation_id.lower()`와 일치.
- 매치된 op들은 결과 맨 앞에 key 오름차순으로 고정되고 `"match": "exact_operation_id" | "exact_operation_id_ci" | "exact_key"`, `score = max(lexical 최고점, 0) + 1.0`. 필터는 그대로 적용.
- 응답에 `"exact_match": bool`.

## 6. 검색 alias (`search.py`, `policy.py`, `data/search_aliases.json`)

### 6.1 데이터 형식
```json
{
  "version": 1,
  "damping": 0.5,
  "aliases": {
    "delete": ["remove"],
    "get":    ["fetch", "read"],
    "update": ["edit"],
    "comment": ["comments"]
  },
  "rules": [
    {"when_all": ["transition", "issue"], "add": ["transitions", "dotransition"]},
    {"when_all": ["update", "page"],      "add": ["updatepage"]},
    {"when_all": ["issue", "key"],        "add": ["getissue"]}
  ]
}
```
- `aliases`: 단일 토큰 → 직접 동의어만. 의도 추론(`status→transitions`, `user→assignee`, `content→body`, `list→search`)은 금지.
- `rules`: `when_all`의 토큰이 **모두** base 토큰에 있을 때만 `add`를 넣는 조건부 규칙. 위험한 확장은 여기로만.
- 모든 토큰은 §13.1 tokenizer 출력 형식(소문자, plural variant 미포함)이어야 하며 로드 시 검증(`policy.py`, 실패 시 `ValueError`).
- seed 내용은 **held-out/negative 벤치마크(§7)를 통과하는 범위에서 구현 시 확정**한다. 위 예시는 출발점이며 벤치마크가 거부하면 뺀다.

### 6.2 적용과 점수
- `base = tokenize(query)`(joined form 포함 §13.1 규칙 그대로). `alias_tokens = ∪ aliases[t] ∪ rules(add) − base`, 각 토큰에 plural variant 적용.
- 점수: `score = Σ_base weight·[hit] + damping · Σ_alias weight·[hit]`. all-match 보너스는 `tokenize(query)`의 원 토큰만으로 판정(alias·joined 제외, Phase 2 규칙 유지).
- 응답 필드: `query_tokens`(원), `alias_tokens`(추가분), `expanded_tokens`(합집합, 정렬). 셋 다 정렬된 list.

## 7. 검색 벤치마크 (`tests/benchmarks/search_queries.json`, `tests/diag_search_queries.py`)

- 세 집합:
  - `seed`: 이번에 관찰된 실패 3개 + Phase 2 §13.5 6개. 회귀 방지용. alias 설계에 사용됨.
  - `held_out`: alias 설계에 **사용하지 않은** paraphrase 12개 이상(예: `attach a file to a jira ticket`, `change issue assignee`, `post a comment on an issue`, `create a new confluence page in a space`, `fetch page by id`, `run jql query`, `add issue to sprint`, `list boards`, `delete an attachment`, `get project by key`, `update page title`, `move issue to backlog`). 각 항목은 기대 key 1개 또는 허용 key 집합.
  - `negative`: alias가 오히려 잘못된 op를 올릴 수 있는 질의 8개 이상(예: `get issue status` → 전이 API가 1위면 실패, `get user`, `list users`, `update issue summary`, `get page property`, `get transitions` → 실제로 `getTransitions`가 정답).
- 파일은 fixture가 아니라 **실제 캐시**(`.atlassian-docs/`)에 대해 진단 스크립트가 돌린다(수동, `sync_all` no-op 주입). 출력: 집합별 1위 정답률과 오답 목록.
- 오프라인 단위 테스트는 `seed` 집합을 fixture 위에서 고정한다(Phase 2와 동일 방식).
- Phase 3 재판정(§18)은 `held_out`·`negative` 기준으로만 한다.

## 8. 검색 질의 로그 (`search_log.py`)

- 활성: 환경변수 `ATLASSIAN_DOCS_SEARCH_LOG` ∈ {`1`,`true`,`yes`}(대소문자 무시). 기본 꺼짐.
- 경로: `storage.CACHE_DIR / "intelligence" / "search_log.jsonl"`.
- 레코드: `{"ts", "query", "filters", "query_tokens", "alias_tokens", "exact_match", "total_matches", "top": [{"key","score"}×≤3], "intelligence_fingerprint"}`.
- `query`는 2,048자로 자르고 제어문자(`\x00-\x1f`)는 공백으로 정규화한다. **주의(문서화):** raw query는 사용자 입력이므로 사용자가 넣은 민감정보가 그대로 남을 수 있다. 로그는 body/header 등 다른 tool 인자를 자동 수집하지 않는다는 보장만 한다.
- 기록 실패(OSError)는 삼킨다. 5 MiB 이상이면 `.prev`로 회전.
- `search_operations`만 기록한다. `get_api_status.refresh.search_log_enabled`로 상태 노출.

## 9. Operation quirks (`quirks.py`, `data/operation_quirks.json`)

### 9.1 모델
```python
@dataclass(frozen=True)
class HeaderQuirk:
    name: str
    value: str | None
    enforcement: str      # "advisory" | "required"
    value_policy: str     # "observed" | "literal"   (literal은 override만 부여 가능)
    origin: str           # "quirk:description" | "quirk:override"
    note: str | None

@dataclass(frozen=True)
class MultipartField:
    name: str
    required: bool
    kind: str             # "file" | "text"
    note: str | None

@dataclass(frozen=True)
class OperationQuirks:
    key: str
    headers: tuple[HeaderQuirk, ...]
    request_hints: dict          # {"multipart_fields": [MultipartField...]} 등, 구조화된 것만
    notes: tuple[str, ...]
    suppressed: tuple[str, ...]  # override로 억제된 mined header 이름
```

### 9.2 Description mining (advisory only)
- 허용 목록 `MINED_HEADERS = ("X-Atlassian-Token",)`.
- 규칙: `` `?(X-Atlassian-Token)\s*:\s*([A-Za-z0-9_-]+)`? `` 매치 → `HeaderQuirk(name, value, enforcement="advisory", value_policy="observed", origin="quirk:description")`. 값 없는 언급은 mining 대상이 아니다(§9.5 candidate scan이 잡는다).
- mining만으로는 어떤 요청도 `missing_required`나 error가 되지 않는다.

### 9.3 Curated override
```json
{
  "version": 1,
  "operations": {
    "jira-platform:POST:/rest/api/3/issue/{issueIdOrKey}/attachments": {
      "headers": [{"name": "X-Atlassian-Token", "action": "set", "value": "no-check",
                   "enforcement": "required", "value_policy": "literal",
                   "note": "Atlassian docs: XSRF check bypass required for multipart uploads"}],
      "request_hints": {"multipart_fields": [{"name": "file", "required": true, "kind": "file"}]},
      "notes": []
    }
  }
}
```
- 키는 canonical key 전체 일치만.
- `headers[].action`: `"set"`(기본) 또는 `"suppress"`(같은 이름의 mined header를 제거하고 `suppressed`에 기록).
- 같은 헤더가 mining과 `set` 양쪽이면 override가 이긴다.
- `enforcement="required"`와 `value_policy="literal"`은 override에서만 설정 가능. 로드 시 스키마 검증(키 형식, enum 값, 타입); 실패는 `ValueError`로 모듈 로드 시 드러난다.
- 초기 seed: 관찰된 4개 op 모두 `required`+`literal "no-check"`로 등록하고, attachments에는 `multipart_fields` 추가. (mining은 향후 새 op를 advisory로 잡는 탐지기 역할.)

### 9.4 계산 시점
`quirks.for_operation(op) -> OperationQuirks`를 template/check가 호출한다(lazy). registry는 그대로.

### 9.5 진단 (status)
- `orphaned_override_keys`: override 키 중 현재 active registry에 없는 것. `get_api_status.diagnostics`에 노출.
- `header_candidates`: 허용 목록 밖의 `X-[A-Za-z0-9-]+` 언급을 description에서 찾아 `{key, header}` 목록으로 노출(자동 적용 없음).

### 9.6 template 반영 (`request_template.py`)
- 헤더 항목 형태: `{"declared_required": bool, "effective_required": bool, "value": ..., "origins": ["spec", "quirk:override"], "effective_origin": "quirk:override", "enforcement": ..., "note": ...}`. `effective_required = declared_required OR (quirk.enforcement == "required")`.
- `missing_required`는 `effective_required`이고 값이 없는 헤더를 포함한다. advisory 헤더가 없으면 `advisories: [{"name","origin","note"}]`에만 나온다.
- `request_hints`를 그대로 출력(`multipart_fields` 등).
- 최상위 `"quirks": {"applied": [...], "advisories": [...], "suppressed": [...], "request_hints": {...}}`.

### 9.7 check 반영 (`request_check.py`)
- `required` 헤더 누락 → error `{"location": "header.X-Atlassian-Token", "rule": "required", "origin": "quirk:override"}`.
- advisory 헤더 누락 → warning `advisory_header_missing`.
- 값 불일치: `value_policy == "literal"` → error `quirk_value_mismatch`; `"observed"` → warning.
- multipart hint가 있고 body가 dict인데 required field가 없으면 warning `multipart_field_missing`(body 구조가 클라이언트마다 달라 error로 두지 않는다).
- `checked`에 `quirk_headers` 추가.

## 10. `intelligence_fingerprint`와 policy provenance (`policy.py`)

```text
POLICY_VERSIONS = {"search": 2, "quirks": 1, "oas_transpiler": 1}
intelligence_fingerprint = sha256(registry_fingerprint + "\n" + aliases_sha256 + "\n" + overrides_sha256 + "\n" + json.dumps(POLICY_VERSIONS, sort_keys=True))
```
- `search_operations`, `build_request_template`, `check_request`, `get_api_status` 응답에 `intelligence_fingerprint`와 `intelligence_policy: {aliases_sha256, overrides_sha256, versions}`를 추가한다. 기존 `registry_fingerprint`/`provenance`는 그대로(스펙 provenance와 policy provenance 분리).

## 11. `jsonschema` 경로 (`oas_schema.py`, `request_check.py`)

### 11.1 의존성
`requirements-validate.txt`: `jsonschema>=4.18,<5`. 모듈 상단 import 금지; `find_spec` 확인 후 함수 안 import. layering test는 `request_check.py`와 `oas_schema.py`에 한해 허용.

### 11.2 OAS 3.0 → draft-07 변환 `oas30_to_draft7(schema) -> dict` (request 방향)
schema-bearing 키워드(`properties`, `items`, `additionalProperties`(dict), `allOf/oneOf/anyOf`, `not`)만 재귀하며 각 노드에서:
1. `nullable is True` **and** `isinstance(type, str)` → `type = [type, "null"]`; 그 외에는 `nullable`만 제거하고 null 허용을 추가하지 않는다(allOf 부모 type 상속에 적용 금지).
2. `exclusiveMinimum is True` → `exclusiveMinimum = minimum`, `minimum` 제거; `False`면 키 제거. `exclusiveMaximum` 동일.
3. `readOnly is True`인 property 이름을 부모 `required`에서 제거하고, 그 property는 `x-readonly-request: true` 표식을 남긴다(검증 후 body에 있으면 warning `readonly_property_present`). `writeOnly`는 required 유지, 키만 제거.
4. OAS 전용 키 제거: `discriminator`, `xml`, `externalDocs`, `deprecated`, `x-*`.
5. 결과에 `Draft7Validator.check_schema()`를 실행; 실패하면 `SchemaError`를 호출자에게 돌려 fallback.

### 11.3 OAS 3.1
`$schema`가 있으면 `jsonschema.validators.validator_for(schema, default=Draft202012Validator)`; 지원하지 않는 dialect(`validator_for`가 default를 돌려주면서 `$schema`가 알려지지 않은 경우) → fallback `unsupported_dialect`. 3.1은 변환 없이 `check_schema()`만.

### 11.4 경로 선택과 fallback 사유
```text
body 있음 and body_schema 있음 and jsonschema 사용 가능
  → resolved = schemas.resolve(body_schema, comps, max_depth=8, max_nodes=2000)
  → unresolved/cycles/truncated → structural ("schema_not_fully_resolvable")
  → transpile(3.0) 또는 dialect 선택(3.1) 실패 → structural ("schema_transpile_failed" | "unsupported_dialect")
  → check_schema 실패 → structural ("jsonschema_schema_error")
  → 검증 중 jsonschema 계열 예외(SchemaError, RefResolutionError 등) → structural ("jsonschema_runtime_error")
  → 성공 → "jsonschema"
jsonschema 없음 → structural ("jsonschema_not_installed")
```
임의의 다른 예외는 삼키지 않는다. 응답: `body_check`, `body_check_reason`.

### 11.5 오류 매핑과 목록
- `{"location": "body" + path, "rule": f"schema:{validator}", "message"}`, 최대 50개, 초과 시 warning `errors_truncated`. path 표기는 `.name` / `[i]`.
- jsonschema 경로: `checked = ["required","type","enum","body_required","content_type","body_not_declared","quirk_headers","jsonschema:body"]`, `not_checked = ["format", "cookie parameters"]`. structural 경로는 Phase 2 목록.
- `format`은 검사하지 않는다(format checker 미지정).
- `compatible = len(errors) == 0`. `valid` 키 없음.

### 11.6 capabilities
`get_api_status.capabilities.validation = {"engine": "jsonschema"|"structural", "version": <jsonschema.__version__|None>, "oas_transpiler_version": 1}`.

## 13. unavailable source refresh 억제 (`manager.py`)
