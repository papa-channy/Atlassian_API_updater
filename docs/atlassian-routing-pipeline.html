atlassian-routing 작동 파이프라인

atlassian-routing은 Jira·Confluence 요청을 받으면 먼저 실행인지 설계인지 가르고, 실행이면 커넥터로, 커넥터에 없거나 설계 요청이면 atlassian-openapi MCP로 보낸다. 5단계 중 1~3단계가 경로를 정하는 라우팅이고, 4~5단계가 REST 명세 산출과 쓰기 확인·보고다.

  • 단계 5개 (라우팅 3 + 명세·확인 2)
  • 재탐색 최대 2회
  • 일치 조건 4가지 (모두 만족)
  • 쓰기 확인 등급 5행
  • SKILL.md 본문 387단어 (상한 500)

출처: .claude/skills/atlassian-routing/SKILL.md, 설계 스펙 docs/superpowers/specs/2026-11-01-atlassian-routing-skill-design.md v0.5. 원문과 다르면 SKILL.md가 맞다.

15단계 흐름

단계를 누르면 아래에 입력, 분기, 규칙, 원문 위치가 나온다. 고정 규칙: REST 요청은 전송하지 않고, 서버 URL·자격증명·curl을 만들지 않으며, "미지원 확인"이라고 말하지 않는다.

      사각 번호 · 라우팅 단계 (실선) 원형 번호 · 명세·확인 단계 (점선) ⚠중단·분기 조건

      2두 계층의 역할

      스킬은 판단만 한다. 실행은 커넥터가, 명세는 OpenAPI MCP가 맡는다.

      커넥터 (실행 계층)

      claude.ai Atlassian 커넥터. 직접 도구와 discover → executeRead/executeWrite/executeDestructive. 자체 operation 이름과 입력 규격을 쓰며 REST 경로가 아니다.

      atlassian-openapi MCP (지식 계층)

      공식 OpenAPI 명세로 요청을 설계·검수한다. Jira·Confluence를 호출하지 않고 URL·자격증명을 만들지 않는다.

      atlassian-routing (판단 계층)

      의도와 도구 가용성을 보고 알맞은 계층으로 연결한다. 하네스 권한을 우회하거나 기대지 않는다.

      33단계 상세: operation 일치 조건

      커넥터 operation은 아래 네 가지를 모두 만족해야 쓴다. 요청은 명확한데 하나라도 안 맞으면 질의를 바꿔 최대 2회 다시 찾고, 그래도 없으면 "커넥터에서 발견되지 않음"이다.

      1. 시작직접 도구가 있으면 그것을 먼저 확인한다. 없으면 discover로 찾는다.
      2. (a) 제품·리소스요청의 제품과 대상이 operation과 같아야 한다.
      3. (b) 작업 의미요청한 동작과 operation의 동작이 같아야 한다.
      4. (c) 입력 매핑대상 식별자와 필수 입력값을 정확히 채울 수 있어야 한다.
      5. (d) 표현 가능operation의 입력 규격으로 요청을 충분히 표현할 수 있어야 한다.
      6. 결과모두 만족하면 사용. 아니면 재탐색 → "발견되지 않음". 다른 제품·대상의 operation은 빌리지 않는다.

      45단계 상세: 쓰기 확인 등급

      쓰기 확인 (이 환경은 하네스가 쓰기를 막지 않으므로 스킬이 확인을 책임진다)
      상황행동
      읽기바로 실행
      대상·필수값 누락묻고 실행하지 않음
      값을 스킬이 추론제안하고 확인 후 실행
      요청이 대상·내용을 확정한 일반 생성·수정바로 실행
      고영향: executeDestructive 분류, 삭제, 한 요청에 3건 이상 변경대상·범위·영향을 요약하고 명시적 승인 후에만 실행 거절·무응답이면 실행 안 함

      승인받은 대상·내용과 다른 입력, 같은 작업의 중복 호출은 하지 않는다. 확인은 잘못된 operation을 골라도 된다는 승인이 아니다.
